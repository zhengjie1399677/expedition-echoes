## 1. 项目北极星

《远征余响》是一个以 {{user}} 为非参战队长、以三名队员为核心的二次元幻想小队远征游戏。

玩家应感受到：自己每天都在为队伍做选择；选择会改变远征的资源、风险与人物反应；角色能与队长自由交谈，但游戏事实始终可信。

当前版本优先完成一个有深度的可重复闭环，而不是堆叠页面、角色数量或美术资产：

```text
城镇接取委托
→ 编队与行囊取舍
→ 远征战斗与事件选择
→ 胜利 / 撤退 / 失败结算
→ 宿舍角色反馈
→ 上楼休息至次日
```

## 2. 当前开发优先级

按顺序推进；没有明确理由时，不跨级扩展。

1. 初始三人：职业技能、战斗反馈、压力反应与宿舍互动。
2. 远征深度：行囊、战斗、事件选择、三种结算以及可见后果。
3. 轻量目标框架：传闻、区域威胁、事件钩子和后续任务，不做强制线性主线。
4. 关系内容：好感阶段、状态触发的 LLM 场景、远征后反应和 LLM 上下文。
5. 统一视觉与音效：可读性、动效、按钮状态、暖色奇幻风。
6. 招募角色：仅在前三名角色的美术、战斗和叙事模板成熟后开始。

近期明确不做：新招募入口、新可玩角色、复杂装备耐久、无限随机任务、要求 LLM 才能运行的核心功能。

## 3. 玩家、角色与叙事原则

- {{user}} 是队长，不参战；队员不能替玩家做重大决定。
- 初始可玩角色只有岚、雾、星罗。角色数量不是当前内容目标。
- 主线不是固定章节清单，而是“目标框架 + 可变路径”。玩家可以选择处理顺序、态度或暂时搁置。
- 人物性格、关系阶段和既有事件必须影响对话，但不应把角色写成只会重复人设标签。
- 关键剧情结果由状态条件触发；LLM 只负责表达、反馈和有限建议。

角色的详细设定见 [GDD.md](GDD.md) §19.15（初始三人人物设定草案）。

## 4. LLM 与确定性规则的边界

### 游戏代码必须负责

- 金币、经验、生命、压力、补给、装备、掉落和任务完成。
- 事件前置、事件选择、区域状态、奖励档位和结局条件。
- 存档、迁移、数值计算和所有可重复验证的规则。

### LLM 可以负责

- 自由宿舍对话、角色语气和好感阶段表现。
- 由游戏状态触发的角色场景：根据远征结果、压力、事件选择和关系阶段生成当下反应。
- 对远征结果、礼物、传闻和事件选择的叙事反馈。
- 在白名单已有的地点、角色、任务模板中提出线索或建议。

### LLM 绝不能负责

- 直接写入游戏状态，或自行确认“任务完成”。
- 发放未定义的道具、数值、角色或区域。
- 覆盖玩家选择、跳过前置条件、编造已成事实的世界信息。

任何未来结构化输出都必须经过：提取 → 格式校验 → 白名单/语义校验 → 领域 action。解析器不得直接修改状态。

## 5. 系统设计约束

### 5.1 远征

- 城镇背包是长期仓库；远征行囊是本次可带入补给，固定上限为 10 格。
- 食物、绷带、镇定剂占用行囊；装备不占格；战利品在结算时入库。
- 每个事件必须提供至少两种可理解的选择，并明确收益、代价或风险方向。
- 事件选择必须在结算、日志或后续状态中留下可见结果。
- 胜利、撤退、失败都必须清楚展示消耗、返还和收益；不能让玩家猜规则。

### 5.2 压力

- 现有 `morale` 是压力值：0 为平静，数值越高压力越大。
- 受击与冒险探查提高压力；休整与镇定剂降低压力；高压力降低战斗表现。
- 首版不做离队、永久损伤或强制失败。压力用于制造取舍，不用于惩罚玩家。
- 后续 UI、文案和变量命名应逐步统一为“压力”；改名必须带迁移与测试，不能只改显示文字。

### 5.3 经济与成长

- 每个新增资源必须同时说明来源、用途、上限和玩家取舍；只有来源没有消耗的资源不加入。
- 装备数值必须进入领域计算，UI 不得只展示“看起来有加成”的数值。
- 每次升级、装备或事件收益都应有可感知的战斗或管理反馈。

### 5.4 状态触发的 LLM 场景

- 不以大量固定短剧情替代自由对话。固定内容只定义触发条件、已发生事实、可选的队长态度和允许改变的关系标记。
- 进入宿舍时，游戏可根据最近远征结果、压力阶段、事件选择、好感和近期记忆构造“场景上下文”，交给 LLM 生成角色的开场与回应。
- LLM 只能叙述角色反应、提出问题或给出情绪反馈；不能修改远征结果、压力、奖励或替队长作决定。
- LLM 不可用时，使用与同一触发条件对应的简短本地降级台词，核心循环不受影响。

### 5.5 双通道对白与请求预算

- 所有依赖 LLM 的互动都必须同时有两条通道：**固定对白**与**LLM 深聊**。
- 固定对白是游戏内容的一部分：即时、可测试、可在离线时完整使用；它承担任务意见、事件第一反应、关键提示和降级文案。
- LLM 通道只在玩家主动追问、输入自由文本或明确选择“展开讨论”时调用；它承担个性化细节与自然延续，不承担必须阅读的信息。
- 打开任务、进入区域、结算或进入宿舍时，不得自动为三名角色分别请求模型。
- 三人需要共同回应同一件事时，默认显示三条预设短句；若玩家选择“听听大家的想法”，最多使用**一次**合并请求生成短小讨论摘要，或让玩家选择一名角色单独追问。
- 每次 LLM 请求须设置明确的上下文上限与输出上限，并将结果缓存到当前场景，刷新页面不得重复消耗。

### 5.6 战斗特效方向

- 当前 Phaser 仅承担战斗画布、角色表现和基础攻击反馈；现阶段视觉效果克制不是引擎限制。
- 不因为追求特效而迁移到 Pixi.js。Phaser 的 WebGL 渲染足以完成粒子、补间、屏幕震动、闪白、轨迹、命中停顿与镜头推进。
- 后续优先建立可复用的效果层：攻击命中、技能施放、受击、击杀、压力临界与结算；先统一节奏与色彩，再增加复杂滤镜。
- 所有效果必须服务于可读性：玩家应能一眼分辨普通攻击、技能、受击、治疗/减压与战斗结束。

## 6. 架构职责

```text
src/content/         静态内容：角色、任务、敌人、装备、事件模板
src/domain/          纯 TypeScript 模型、规则、reducer、数值计算
src/infrastructure/  存档、资源预加载、LLM 适配与降级
src/ui/              React/Phaser 展示与输入，不计算核心规则
public/assets/       角色、背景和 UI 图像资源
docs/                产品设计、规范和记录
```

- `content` 不读取运行状态、不执行随机逻辑。
- `domain` 不访问 React、DOM、`localStorage`、网络或 LLM。
- `infrastructure` 不决定游戏规则。
- `ui` 只渲染领域结果、派发 action；不能在组件中修改金币、伤害、掉落或事件结果。
- Phaser 只表现战斗，不拥有战斗真相；真相保留在 `domain`。

## 7. 功能实施流程

任何非微小文案修改按以下顺序进行：

1. 在设计文档写清楚玩家目标、输入、结果、失败方式和不做什么。
2. 确认它属于现有优先级，且不会绕开本文的边界。
3. 在 `content` 定义静态内容，在 `domain` 定义模型和 action。
4. 先写或更新领域测试，再接入 reducer 与 UI。
5. 接入 UI 时提供禁用状态、空状态、错误提示和清晰的结果反馈。
6. 新增持久字段时同步处理存档迁移。
7. 运行测试和生产构建；涉及交互或画面时做本地手动检查。
8. 将“已实现 / 规划中”的状态更新到设计文档，避免文档与代码混淆。

不要为了赶进度直接把规则写进 `App.tsx`，也不要用一次性 CSS 覆盖掩盖结构性 UI 问题。

## 8. 状态、存档与迁移

`GameState.version` 是存档契约。新增或变更持久状态时，必须同时：

1. 更新类型与初始状态。
2. 在 `storage.ts` 为旧档提供安全默认值和清洗逻辑。
3. 更新版本范围与旧 key 迁移策略（必要时）。
4. 为旧档、缺字段、非法字段各写一项测试。
5. 确认新字段不会让玩家因旧档卡死。

禁止用“读不到字段就重置整档”替代迁移，除非存档已经无法安全解析。

## 9. UI、美术与可访问性

- 视觉基调：温暖奇幻、羊皮纸、深木、铜金、赭红；避免大面积绿色 UI 底色。
- 人物是年轻、二次元幻想风；宿舍为无武器的日常装，战斗素材与宿舍素材分开维护。
- 新按钮必须有默认、悬停、禁用和键盘焦点状态，文字与背景有足够对比度。
- 任何关键操作都不能被底栏、浮层或背景遮挡；16:9 和较窄窗口都要检查。
- 生成或导入图像前先确认它是否真的补足玩法/氛围，不为填空而增加资产。
- UI 文字显示应使用领域层最终结果，不能复制一套独立计算。

## 10. 测试与验收

领域规则变更必须有对应测试，至少覆盖：

- 正常路径；
- 边界值和资源不足；
- 重复 action 或非法 action；
- 与存档/结算相关的状态回收；
- 新功能不会破坏既有远征、每日循环或装备计算。

功能完成最低标准：

- `npm test` 通过。
- `npm run build` 通过。
- 旧存档可安全载入或有明确迁移。
- 关键操作在本地可走通，控制台无新错误。
- LLM 不可用时，核心流程仍然可玩。
- 文案、按钮、结果反馈和视觉状态与规则一致。

## 11. 提交与重构原则

- 一次提交只解决一个可描述的问题；不要把机制、全面格式化和无关美术改动混在一起。
- 工作区有其他未提交内容时，只修改任务必需的最小范围，不覆盖、不重置他人改动。
- 重构先保留行为，再分文件；若规则改变，必须明确为“玩法改动”并补测试。
- 出现两个以上页面复制同一规则或同一数值时，抽到 `domain`/`content`，不要继续复制。
- 新的“临时方案”必须标注退出条件；没有退出条件的临时方案会变成永久债务。

## 12. 近期里程碑

### M1：可重复远征

三人职业差异、10 格行囊、战斗/事件选择、三种结算、压力反馈完整可玩。

### M2：会回应队长的队伍

远征后宿舍对话、好感阶段、少量个人事件和可控 LLM 上下文。

### M3：轻量世界推进

传闻、区域威胁、事件后果和任务变化构成目标框架；仍允许玩家自由选择。

### M4：内容扩展

在角色美术/行为模板成熟后，逐个制作新的可招募角色与对应完整内容。

## 13. 美术与界面规范（原 UX_ART_BEHAVIOR_GUIDE.md）

### 13.1 产品形态

- 本项目是嵌入式游戏，不是由纵向内容块组成的普通网页。
- 桌面端与移动端都必须在当前视口内形成一个完整游戏舞台。
- 页面本身不得无限向下延伸；需要查看更多内容时，只允许指定面板内部滚动。
- React 负责界面、导航、存档和 LLM 交互；Phaser 负责远征中的场景、动画、镜头、粒子与音频。
- 即使 LLM 不可用，所有游戏规则、导航和远征流程仍须完整运行。

### 13.2 导航行为

- 城镇地图是非战斗功能的唯一主导航。
- 酒馆、宿舍和城门通过地图中的地点进入，不在顶部重复提供入口。
- 设置是系统级功能，放在右上角，不作为地图地点。
- 子页面提供“返回城镇”；点击游戏标题也可返回城镇。
- 酒馆必须进入独立页面，不得在地图下方展开网页式长面板。
- 远征完成或撤退后返回城镇地图。

### 13.3 固定舞台与滚动

- 应用根节点占满 `100dvh`，浏览器正文禁止滚动。
- 顶栏高度由内容决定，剩余空间全部交给当前游戏界面。
- 城镇地图、宿舍和战斗舞台默认不产生页面滚动。
- 酒馆队员列表、设置列表等可能溢出的内容，应在各自面板内部滚动。
- 战斗 HUD、地图和日志必须在同一个视口中可见，不得要求玩家上下翻页操作一回合。
- 移动端通过重新排版、缩放和局部滚动适配，不得简单变成长网页。

### 13.4 地图热点

- 地点标签应像地图注记一样融入背景，不使用明显矩形卡片、玻璃面板或大面积底色。
- 默认只显示文字、用途和小型定位标记。
- 悬停只能改变光点、文字亮度或极轻微光晕，不得突然出现另一套卡片样式。
- 交互热区可以大于视觉标记，但不可用可见底板表达热区。

### 13.5 整体美术方向

- 青春日式幻想冒险风，约六头身，年轻但不幼儿化，不使用写实成年佣兵比例。
- 采用清晰线稿、简化结构、平涂与少量分级阴影，避免写实金属、皮革和肌肉质感。
- 角色使用明亮职业配色；环境相对低饱和，以保证角色可读性。
- 酒馆、宿舍、城镇与远征必须属于同一个世界，不得出现写实背景与动漫角色互相拼贴。
- 可以参考用户提供图片的温暖空气感与青春幻想氛围，但不得复刻其中人物、服装、构图或识别性元素。

### 13.6 战斗画面

- 横版舞台，三人队伍同时站场，场景和距离关系是主体。
- 角色实际可见高度不应长期超过战斗区域高度的约三分之一。
- 前景、中景、远景必须清晰分层，角色脚下要有可信的地面位置。
- 动作采用约 12 FPS 的序列帧；镜头、根位移、粒子和界面以实时帧率运行。
- 攻击动作中的前进由 Phaser 世界坐标控制，序列帧只表现身体动作，禁止“角色迈步但原地不动”。
- 命中反馈至少包含关键帧停顿、受击动作、位移或击退、音效/粒子和适度镜头反馈。

### 13.7 动画资产生产

- 禁止让生成器把多个紧贴人物直接画在一张图后再等分裁切。
- 每个关键帧应独立生成和抠图，保留足够安全边距。
- 每帧独立检测可见边界，并以脚底与身体中心建立统一锚点。
- 通过工具在生产末端打包精灵图和帧元数据，而不是把生成画布直接当作精灵图。
- 新角色先完成静态设定、场景合成验证和单个动作样片，通过后再批量生产。
- 废弃原型不得继续作为新美术的约束；正式资产必须使用版本化文件名。

### 13.8 现有美术资产重制与替换

- 用户要求“升级、重做、提高清晰度或增加细节”时，默认属于高保真重制，不等于重新设计；必须锁定原图的画风、构图、视角、色彩关系、地标位置和界面热点对齐。
- 除非用户明确同意改变美术方向，否则禁止只根据文字描述重新生成一张同题材但不同画风、不同构图的新图来替换现有资产。
- 最终资产的原生有效分辨率不得低于被替换资产及目标显示尺寸；禁止把较小的生成图放大后当作高清成品。画布尺寸、文件体积和插值放大都不能视为真实细节提升。
- 必须优先使用现有原图作为编辑目标或高保真参考。若工具无法读取原图、无法锁定参考风格，或输出分辨率不足，应停止替换并明确报告限制，不得擅自降级为无参考重绘。
- 新版本必须使用版本化文件名并保留旧版。接入前先提供非破坏性预览，在实际目标视口（桌面端至少按 1920×1080、浏览器 100% 缩放）检查清晰度、裁切、构图、画风和热点位置。
- 未经用户确认预览通过，不得把新图切换为默认生产资产；确认后再更新代码引用。用户要求回退时，必须恢复原引用，并按用户要求移除失败版本。

### 13.9 主角、玩家视角与 LLM 边界

- 主角是不直接参战的远征队长；三人战斗阵容只包含队员，主角不得加入冒险者名册或占用战斗站位。
- 游戏叙事以主角为中心。招募、编队、接受委托、下达战术指令、使用补给、撤退以及与队员交谈，都被视为主角在世界中的行为。
- 在 LLM 提示词和角色卡中，主角统一使用 `{{user}}` 占位符，不预设固定姓名。
- 玩家完全控制 `{{user}}` 的语言、心理和决定。LLM 只生成队员与环境对 `{{user}}` 的回应，不得替 `{{user}}` 发言、补充心理活动或擅自采取行动。
- 宿舍等交谈场景默认采用主角视角：队员面向镜头与 `{{user}}` 交流；界面应明确标注玩家输入属于队长。
- 主角可通过城镇背影、地图棋子、对话署名或个人资料建立存在感，但这些表现不得削弱队员作为战斗画面主体的地位。

### 13.10 内容优先级

1. 远征战斗达到完整、可重复游玩的功能品质。
2. 城镇地图与酒馆/宿舍形成完整往返流程。
3. 宿舍与 LLM 情感互动增强。
4. 扩充任务、补给、角色和远征内容。


### 13.11 战斗人偶资源管线（原 COMBAT_RIG_PIPELINE.md）

#### 目标

让新角色、时装、武器与饰品的加入成本接近“替换资源包”，而不是重新制作所有动作帧。

#### 表现层分工

- 酒馆、宿舍与 LLM 互动使用高质量角色插图。
- 战斗使用约六头身的模块化人偶。
- 战斗人偶使用职业骨架、外观皮肤与装备附件三个层级组合。

#### 人偶槽位

每个职业骨架最多使用以下槽位：

1. 基础躯干与下装。
2. 头部与发型。
3. 前后手臂。
4. 前后腿部。
5. 主手武器。
6. 副手装备。
7. 披风、围巾、头发等次级运动附件。

#### 可复用规则

- 新角色优先复用已有职业骨架，仅替换脸、发型、配色、服装皮肤和附件。
- 新时装只替换服装皮肤与附件。
- 新武器只替换武器槽位，并可附带少量动画参数。
- 只有新增职业或非人骨架时，才需要新建动作集。
- 同一人偶动作由根位移、骨架姿势和附件延迟组成；禁止整张人物图上下漂浮。

#### 锚点与动作

- 双脚与根节点始终固定到场景地面基线。
- 待机只改变胸肩、头部、头发、围巾和武器的局部姿势。
- 攻击的实际前进与返回由 Phaser 世界坐标控制。
- 命中时以关键帧停顿、受击反应和镜头/特效表达冲击。

#### 资源格式

- 原始部件表使用纯色键背景。
- `scripts/extract_rig_parts.py` 根据 alpha 连通块裁出部件，并生成可复查的 JSON 清单。
- 任何自动裁边后的部件都保留原始表和清单，供人工命名、确认槽位和调整锚点。
- 只有经过人工确认的部件清单才可以进入运行时人偶定义。

#### 当前原型

`pipeline-assets/rigs/lan-vanguard-v1/parts-sheet-v1.png` 是先锋人偶的首张部件表。它目前只验证资产分离与自动裁边流程，不替换战斗中的正式角色。该目录属于资产管线产物，存放在 public/ 之外，不进入游戏运行时构建。

## 14. 代码审查标准与流程（原 CODE_STANDARD.md）

> 状态：生效中（2026-08-06 制定，2026-08-07 重建恢复）。代码合入与功能交付前的审查依据。
> 与本节所在文件的关系：本文件 §1–§12 管「怎么做对」，本节管「怎么确认做对了」。本节所有红线均引用 §1–§12 的既有边界，不新增设计。

### 1. 文档定位

- 本文件 §1–§12 定义北极星、架构职责、状态/存档规则与功能实施流程——它是「做对」的施工图。
- 本文把上述边界转成**可判定的审查动作**：分级、维度、红线、流程与报告约定——它是「确认做对」的验收尺。
- 二者冲突时以本文件 §1–§12 为准；本节只负责判定，不改变规则。

### 2. 三级分级

| 级别 | 含义 | 合入影响 |
|---|---|---|
| 🔴 **Blocker** | 必须修。违反红线、破坏核心规则正确性、数据安全或玩家可玩性 | 阻塞合入 |
| 🟡 **Suggestion** | 应修。影响体验、维护性或覆盖缺口，但不破坏正确性 | 可带修复计划合入，当周闭环 |
| 💭 **Nit** | 风格、命名、排版等主观问题 | 不阻塞，随缘清理 |

#### 2.1 判定决策树

```text
违反红线速查（§7 十五条之一）？─────────────────────────► 🔴 Blocker
否
导致存档丢失/损坏、旧档卡死、玩家无法继续？─────────────► 🔴 Blocker
否
核心规则（金币/伤害/掉落/事件结果/补给消耗）与设计不符？─► 🔴 Blocker
否
LLM 越权（写状态/发未定义物/跳过前置/确认完成）？───────► 🔴 Blocker
否
影响体验但可绕过、仅缺反馈、死代码、测试缺口？─────────► 🟡 Suggestion
否
纯风格/命名/排版/可读性问题？────────────────────────► 💭 Nit
```

#### 2.2 历史判例表（以 2026-08-06 全项目审查 26 项为基准）

| 判例 | 问题性质 | 判定 | 判定理由 |
|---|---|---|---|
| 威胁预告 UI 缺失（敌人意图不渲染） | 高严重 | 🔴 Blocker | 核心「读题→解题」玩法在玩家界面是空的，体验链路断裂 |
| 事件补给白嫖（recover 不校验 requirement/不扣消耗） | 逻辑错误 | 🔴 Blocker | 奖励/消耗与设计不符，玩家可白嫖，规则正确性被破坏 |
| 结算瞬间弹空壳晨报（pending 未处理） | 逻辑错误 | 🟡 Suggestion | 显示错误但不破坏存档正确性 |
| 背包面板 key 大小写错误 + 错读数据源 | 逻辑错误 | 🟡 Suggestion | 功能可用但展示数据错误，可绕过 |
| 死 action 仅测试驱动（SWAP/DEESCALATE 等） | 失效/废弃 | 🟡 Suggestion | 不破坏正确性，但增加维护面与误导 |
| 错误类 9 个仅测试引用 | 失效/废弃 | 🟡 Suggestion | 同上 |
| 城门锁定态可点击（交互误导） | 未完成/占位 | 🟡 Suggestion | 影响引导但无数据风险 |
| 装备图标 emoji 占位 | 未完成/占位 | 💭 Nit | 视觉占位，不阻塞功能 |
| 无效导入 / 死 prop / 多余导出 | 失效/废弃 | 💭 Nit | 纯卫生问题 |

### 3. 分级审查

按**改动规模与影响面**选档，避免一刀切：小改动不拖全流程，大改动不许漏检。

| 档位 | 触发条件 | 覆盖 |
|---|---|---|
| **全面审查** | 跨层改动（domain + ui + infrastructure + content）；存档契约变更；新系统/新页面；新增或修改 Phaser 场景；重构涉及规则 | 全部 9 个维度（§4），AI + 人工交叉审查，跑完整机器检查 |
| **标准审查** | 单层改动：领域规则 + 测试；UI 组件增改（不触及核心规则）；content 内容增改 | 维度 1/4/7 必查，其余按改动面抽查 |
| **轻量审查** | 纯文案、样式微调、重命名（带迁移则升档）、死代码删除、单文件小改 | 自审 + 机器检查；对照 §7 十五条速查 + §6 写作规范 |

默认走**标准审查**；拿不准时升档不降档。涉及 Phaser、存档迁移、LLM 通道的改动一律**全面审查**。

### 4. 九个审查维度

每个维度：**项目红线**（违反即 🔴）+ **常见问题**（多为 🟡/💭，供快速对号）。

#### 维度 1：领域规则与数值正确性
**红线**
- 金币/经验/生命/压力/补给/装备/掉落/任务完成的计算不在 domain reducer 内（出现在 ui/组件/Phaser 中）→ 🔴
- 数值与设计文档（GDD（含战斗意图 §16）/ BALANCE_TABLE）不符且无设计变更记录 → 🔴
- 事件选择无可见落点（结算/日志/后续状态均无痕迹）→ 🔴
- 事件未提供至少两种可理解的选择，或未明确收益/代价/风险 → 🔴

**常见问题**
- 装备加成只显示「看起来有加成」，未进入领域计算（GUIDE §5.3）
- recover/结算分支不兑现 requirement、不扣消耗 → 白嫖（判例 L2）
- 数值硬编码在组件；边界（0 生命、资源不足、重复 action）未处理
- 日志/文案与真实数值不符（all_damage 虚高、risk_fight 文案与掉落不符）

#### 维度 2：架构职责与分层边界
**红线**
- `domain` 访问 React / DOM / `localStorage` / 网络 / LLM → 🔴
- `content` 读取运行状态或执行随机逻辑 → 🔴
- `infrastructure` 决定游戏规则 → 🔴
- `ui` 组件内计算并写入核心规则（金币/伤害/掉落/事件结果）→ 🔴
- 两个以上页面复制同一规则/同一数值而未抽到 domain/content → 🔴

**常见问题**
- 规则直接写进 `App.tsx`；用一次性 CSS 覆盖掩盖结构问题（GUIDE §7）
- 组件内 import domain 后重算一份结果，与真实状态分叉
- 解析器/适配器直接 dispatch，未经领域校验

#### 维度 3：LLM 边界与降级
**红线**
- LLM 输出直接写入游戏状态，或自行确认「任务完成」→ 🔴
- LLM 发放未定义的道具、数值、角色或区域 → 🔴
- 结构化输出未走「提取 → 格式校验 → 白名单/语义校验 → 领域 action」→ 🔴
- 依赖 LLM 的互动无双通道（固定对白 + LLM 深聊）→ 🔴
- LLM 不可用时核心流程不可玩（无本地降级台词）→ 🔴
- LLM 请求无上下文/输出上限，且结果不缓存（刷新重复消耗）→ 🔴

**常见问题**
- 打开任务/区域/结算/宿舍时自动为三名角色分别请求模型（GUIDE §5.5）
- LLM 返回数值被 UI 直接采用，未过白名单/语义校验
- 解析失败无本地修复或安全回退路径

#### 维度 4：状态、存档与迁移
**红线**
- 新增/变更持久字段未同步：类型+初始状态、`storage.ts` 安全默认值与清洗、版本范围与旧 key 策略、对应测试 → 🔴
- 用「读不到字段就重置整档」替代迁移（除非存档已无法安全解析）→ 🔴
- 新字段导致玩家旧档卡死 → 🔴
- 字段改名（如 morale → 压力）未带迁移与测试，只改显示文字 → 🔴

**常见问题**
- `SUPPORTED_VERSION_MIN` 与迁移链不一致（当前基线 v12，SUPPORTED_VERSION_MIN=12，勿回退）
- 旧档/缺字段/非法字段三类测试缺失
- 跨过 `storage.ts` 直接读写 `localStorage`
- 迁移链残留大量死 key（V5–V11 已收缩，勿复活）

#### 维度 5：UI 展示、交互与反馈
**红线**
- UI 显示的数值非领域层最终结果（另复制一套独立计算）→ 🔴
- 结算/结果不展示消耗、返还与收益，让玩家猜规则 → 🔴
- 关键操作被遮挡/无法触发；无禁用/空态/错误提示 → 🔴
- 新按钮缺默认/悬停/禁用/键盘焦点状态，文字对比度不足 → 🔴

**常见问题**
- 空壳晨报/空壳面板在结算瞬间弹出（pending 状态未处理）
- 锁定态可点击（城门引导失效）；16:9 与窄窗口未检查
- emoji/菱形占位图标（如无资源，先标注待美术，不得假装完成）

#### 维度 6：Phaser 生命周期与表现
**红线**
- 新增/修改 Phaser 场景未走 `BattleCanvasBoundary` + 延迟创建模式（React 19 StrictMode 下 unmount/remount 竞态）→ 🔴（黑屏类 bug 高发区）
- Phaser 拥有战斗真相或在场景内重算战斗结果（真相必须保留在 domain）→ 🔴
- 表现与 domain 结算不一致（如动画只表现单体、实际多目标掉血）→ 🔴
- 效果不可读（无法分辨普攻/技能/受击/治疗/战斗结束）→ 🔴

**常见问题**
- 组件卸载后异步回调 setState（缺 cancelled 标志/非ce 消费）
- 引用未预加载纹理；引用不存在的 rig/路径（死代码）
- 反馈 effect 缺依赖项 → 首帧后失效的回归（判例 L1）

#### 维度 7：测试覆盖与可验证性
**红线**
- 领域规则变更无对应测试 → 🔴
- 存档/迁移变更无旧档/缺字段/非法字段测试 → 🔴
- 新 action 无重复 action、非法 action、资源不足边界测试 → 🔴
- 测试断言为空或恒真（无实质 expect）→ 🔴

**常见问题**
- 只测正常路径，缺边界/回收/回归覆盖
- 测试仅驱动死代码（action/类/字段无生产引用）→ 判 🟡 并标记清理
- flaky 测试（依赖时序/随机/外部资源）：必须隔离或修复，不得污染 CI 信号
- 测试命名不表达行为（`test('works')`）

#### 维度 8：内容与资源完整性
**红线**
- 新增资源未同时说明来源、用途、上限与玩家取舍（只有来源无消耗）→ 🔴
- 为填空而增加无来源无用途的资产 → 🔴
- 假透明（RGB 棋盘格）、AI 水印、半透明黑底素材入库 → 🔴
- 代码引用不存在的纹理/路径 → 🔴

**常见问题**
- 素材 RGB 无 alpha 却显示「棋盘格透明」；非像素立绘缺边缘过渡
- 大体积 PNG 未压缩（world/ 场景图应 webp q82）
- 像素风（pixel/）二值化 alpha 是风格特性，不按锯齿误报（MEMORY 美术规范）
- 新增素材未过 `scripts/check_alpha.py`

#### 维度 9：提交与工程卫生
**红线**
- 一次提交混杂机制改动 + 全面格式化 + 无关美术 → 🔴
- 重构改变规则未明确为「玩法改动」并补测试 → 🔴
- 临时方案无退出条件（会沉淀为永久债务）→ 🔴

**常见问题**
- 死代码/无效导入/多余导出残留（判 🟡）
- 大面积格式化混入功能提交，diff 不可审
- 覆盖/重置他人未提交改动；revert 误伤范围
- 提交信息不说明「改了什么 + 为什么」

### 5. 审查流程

```text
自审清单 → 机器检查 → AI + 人工交叉审查 → 合入门槛（0 Blocker）→ 记录复盘
```

#### 5.1 自审清单（开发者提交前）
- [ ] 红线速查 15 条（§7）逐条过，无红线级问题
- [ ] 需求对应 Story/GDD 验收标准可逐条勾选
- [ ] 分层边界：改动落在正确目录，无跨层越权
- [ ] 相关测试已写或已更新（含边界与非法输入）

#### 5.2 机器检查
```powershell
npm test          # vitest run：领域 + 基础设施测试
npm run build     # tsc -b + vite build：类型 + 产物
```
- 三项全绿才进入人工审查；任一红即未达 QA。
- `npm run build` 直接执行即可（safe-delete 插件已从 vite.config.ts 移除）。若未来再遇 dist 清理失败，用 `vite build --outDir dist-verify --emptyOutDir false` 验证产物。
- **环境限制（safe-delete）**：删除文件一律用单条 `Remove-Item -LiteralPath <file> -Force -ErrorAction SilentlyContinue`；**禁止 git rm 批量删含未入库文件的目录**（会级联删除整个目录，未跟踪文件永久丢失，曾致 CODE_REVIEW_STANDARD.md 误删）。

#### 5.3 AI + 人工交叉审查
- 按分级档位（§3）跑对应维度；AI 负责静态扫描 + 交叉引用 + 断言统计，人工负责体验判定与设计意图核对。
- 每条意见按 §6 写作规范落笔，编号引用。

#### 5.4 合入门槛
- **0 Blocker** 才允许合入；🟡 可带修复计划合入（当周闭环）；💭 不阻塞。
- 涉及存档迁移、LLM 通道、Phaser 场景的改动，合入前必须人工确认浏览器实测无新 console 错误。

#### 5.5 记录复盘
- 产出审查报告 `docs/CODE_REVIEW_YYYY-MM-DD.md`（命名约定见 §8）。
- 复盘沉淀：新红线入 §4/§7，新判例入 §2.2，环境坑入项目记忆。

### 6. 意见写作规范

一条合格审查意见必须同时满足：

1. **定位到行**：`文件:行号`，如 `src/ui/BattleCanvas.tsx:635`；不写「某文件有问题」。
2. **说清后果**：指出影响面——数据正确性 / 玩家可玩性 / 维护成本，并说明「为什么这是问题」。
3. **给可执行建议**：具体改法（补参数、加校验、删代码、抽模块），而非「请优化」。
4. **一条一主题**：每条意见只谈一个问题；复合问题拆多条。
5. **标注分级 + 编号**：🔴 B1 / 🟡 S1 / 💭 N1，报告内连续编号便于引用（也可加类型前缀 L/U/D 表示逻辑/未完成/死代码）。

反例：`Expedition.tsx 这里逻辑有点乱，建议重构。`
正例：`src/ui/pages/Expedition.tsx:245 技能槽硬编码 1 个启用、其余 disabled；后果：多技能系统（skills[]）在 UI 只暴露一个，玩家无法使用第二个技能；建议：按 activeHero.skills.slice(0,2) 动态渲染，并为越界情况补空态。🟡 S3`

### 7. 红线速查 15 条（提交/合入前逐条过）

1. LLM 输出直接写入游戏状态，或自行确认「任务完成」。
2. LLM 发放未定义的道具/数值/角色/区域。
3. `domain` 访问 React / DOM / `localStorage` / 网络 / LLM；`content` 读运行状态。
4. `ui`/Phaser 组件内计算并写入金币/伤害/掉落/事件结果（绕过领域）。
5. Phaser 拥有战斗真相，或在场景内重算战斗结果。
6. 持久字段变更未同步：类型+初始状态 / `storage.ts` / 版本 / 测试。
7. 用「重置整档」替代迁移；新字段导致旧档卡死。
8. 新增资源未说明来源/用途/上限/取舍；为填空加资产。
9. 装备/数值只显示在 UI，未进入领域计算。
10. LLM 互动无双通道，或降级后核心流程不可玩。
11. LLM 请求无上下文/输出上限，且结果不缓存（刷新重复消耗）。
12. 领域规则变更无测试；迁移无旧档/缺字段/非法字段测试。
13. 新按钮缺默认/悬停/禁用/焦点状态；关键操作被遮挡；结算不展示消耗/返还/收益。
14. 假透明/水印/黑底素材入库；引用不存在的纹理/路径。
15. 一次提交混杂无关问题；临时方案无退出条件；重构改变规则未补测试。

### 8. 审查报告命名约定

- 报告落点：`docs/CODE_REVIEW_YYYY-MM-DD.md`（如 `docs/CODE_REVIEW_2026-08-06.md`）。
- 报告结构：审查范围（分级档位 + 覆盖维度）→ 机器检查结果（测试/构建/类型）→ 意见清单（按 §6 编号）→ 分级汇总（🔴/🟡/💭 计数）→ 合入门槛判定（PASS / CONCERNS / FAIL）→ 待办与下一步。
- 报告属于**过程记录**，非设计文档；归档策略按主理人指示执行，删除时遵守 §5.2 的 safe-delete 约束。

## 15. 历史技术参考（原 DEVELOPMENT_GUIDE.md）

> 本节保留早期技术细节。项目当前唯一生效的整体规范为本文件 §1–§12（PROJECT_DEVELOPMENT_GUIDE.md）；如两者冲突，以整体规范为准。

> 面向后续维护、功能扩展和与 Mobile-Tavern / SillyTavern 的集成。

### 1. 技术栈

- React：页面、管理界面和宿舍对话。
- TypeScript：领域模型、状态和适配器。
- Phaser：远征战斗场景与动画。
- Vite：开发与生产构建。
- Vitest：领域规则和基础设施测试。

常用命令：

```powershell
npm run dev
npm test -- --run
npm run build
```

提交功能前至少运行测试和生产构建。

### 2. 目录职责

```text
src/
  content/
    静态游戏内容：角色、任务、敌人、装备、节点等
  domain/
    领域类型、纯规则、reducer 和战斗数值
  infrastructure/
    存储、资源预加载、LLM 后端适配
  ui/
    React 页面、Phaser 场景和界面行为

public/assets/
  actors-v2/          当前动漫角色战斗素材
  pixel/              像素战斗素材
  portraits-dorm/     宿舍日常立绘
  world/              城镇、酒馆、宿舍和战斗背景

docs/
  设计、流程和开发文档
```

### 3. 架构边界

#### 3.1 `content`

只描述静态内容，不处理运行状态。例如：

- 角色基础信息。
- 任务模板。
- 装备定义。
- 敌人定义。
- 事件模板。
- 品质和奖励档位。

#### 3.2 `domain`

负责可测试的确定性规则：

- 接取和完成任务。
- 每日限制。
- 食物消耗。
- 好感变化。
- 装备打造与出售。
- 战斗伤害。
- 事件状态推进。

不要在 reducer 内执行网络请求、读写 DOM 或调用 LLM。

#### 3.3 `infrastructure`

负责外部系统：

- `storage.ts`：本地存档与迁移。
- `llm.ts`：Mobile-Tavern、SillyTavern 和离线回退。
- 未来的 XML 提取、结构化校验与叙事缓存。

#### 3.4 `ui`

负责展示和用户输入。UI 可以调用基础设施服务，但不能自行计算重要经济或战斗规则。

### 4. 状态版本与迁移

当前存档版本由 `GameState.version` 管理。

新增持久状态时：

1. 修改 `GameState`。
2. 更新 `createInitialGame()`。
3. 增加对应 action 和 reducer。
4. 更新 `storage.ts` 迁移。
5. 为旧版本存档提供安全默认值。
6. 增加迁移测试。

不要因为新增字段直接丢弃旧存档。

以下规划状态应在实施时统一升级版本：

- 游戏天数。
- 今日任务状态。
- 食物库存和饥饿层数。
- 好感度与关系阶段。
- 每日赠礼次数。
- 活跃事件链。
- 每日新闻缓存。
- 角色长期记忆。

### 5. 战斗与装备规则

装备数值必须进入 `domain/gameEngine.ts` 的确定性计算，不允许只显示在 UI 上。

实现新装备效果时：

1. 在内容层定义装备。
2. 在领域层解析装备加成。
3. 将加成用于伤害或减伤计算。
4. 为装备限制和数值结果增加测试。
5. UI 只读取最终属性或加成摘要。

LLM 不能返回任意装备数值。LLM 只能引用现有装备、配方或奖励档位。

### 6. 聊天后端适配

入口文件：

[llm.ts](../src/infrastructure/llm.ts)

支持的提供方：

```ts
type NarrativeProvider =
  | 'auto'
  | 'mobile-tavern'
  | 'sillytavern';
```

#### 6.1 自动选择

```text
Mobile-Tavern 可用
→ 使用 Mobile-Tavern

否则 SillyTavern 可用
→ 使用 SillyTavern

否则
→ 离线对白
```

提供方偏好是设备连接设置，单独保存在 `localStorage`，不属于游戏进度。

#### 6.2 Mobile-Tavern

使用宿主注入：

```ts
window.MobileTavernPlugin.llm.chat({
  messages,
  sampling: {
    temperature: 0.8,
    max_tokens: 220,
  },
});
```

打包为 Mobile-Tavern 插件时，清单必须声明：

```json
{
  "permissions": ["llm.chat"]
}
```

本游戏不会管理 Mobile-Tavern 的模型地址或密钥。

#### 6.3 SillyTavern

使用稳定扩展上下文：

```ts
const context = window.SillyTavern.getContext();
const result = await context.generateRaw({
  systemPrompt,
  prompt: messages,
});
```

不要直接导入 SillyTavern 内部模块路径。其官方建议使用 `getContext()`。

本游戏不会管理 SillyTavern 的模型地址或密钥。

#### 6.4 对话上下文

发送给模型的内容包括：

- 角色名称、性格和当前关系阶段。
- 当前地点。
- 最近游戏事件。
- 最近玩家和角色消息。
- 当前玩家输入。

禁止在系统提示中要求模型修改游戏数值。

### 7. 结构化叙事

建议新增独立模块：

```text
src/infrastructure/narrativeProtocol.ts
src/domain/narrativeValidation.ts
```

职责划分：

- `narrativeProtocol.ts`
  - 提取 XML。
  - 去除代码围栏。
  - 进行有限格式修复。
  - 解析为未知数据。
- `narrativeValidation.ts`
  - 验证允许标签。
  - 验证 ID 和枚举。
  - 验证事件前置状态。
  - 将安全指令转换为领域 action。

不要让解析器直接 dispatch。

推荐处理流：

```text
LLM 原始回复
→ 提取信封
→ XML 解析
→ 结构校验
→ 语义校验
→ 生成候选叙事动作
→ reducer 应用合法动作
```

### 8. 原生结构化能力

未来 Mobile-Tavern 可以扩展能力查询，但游戏不能依赖它一定存在：

```ts
interface LlmCapabilities {
  structuredOutput: boolean;
  streaming: boolean;
  maxContextTokens?: number;
}
```

调用策略：

```text
支持 Schema
→ 原生结构化请求

不支持 Schema
→ 普通文本请求，要求 XML

解析失败
→ 本地修复

仍失败
→ 保留安全文本或使用离线模板
```

无论是否支持 Schema，都必须执行游戏语义校验。

### 9. 日程系统的推荐实现顺序

第一阶段：

1. 增加游戏天数。
2. 增加“今日是否已接任务”。
3. 限制每天一次任务。
4. 增加休息至次日。

第二阶段：

1. 增加普通食物。
2. 每进入节点消耗一份食物。
3. 食物不足时增加饥饿层数。
4. 将惩罚接入战斗计算。

第三阶段：

1. 增加任务材料奖励。
2. 增加材料出售。
3. 增加装备打造配方。
4. 打造装备进入现有背包。

第四阶段：

1. 增加礼物与角色偏好。
2. 增加好感与阶段门槛。
3. 将关系阶段注入聊天提示。
4. 增加阶段突破事件。

第五阶段：

1. 每日新闻缓存。
2. XML 叙事协议。
3. 特殊任务提议。
4. 事件链串联和次日反馈。

### 10. 测试要求

领域功能必须优先测试：

- 每天只能接一次任务。
- 撤退不能返还任务次数。
- 每个节点只消耗一次食物。
- 食物不足不会造成死档。
- 材料出售数量和金币正确。
- 打造消耗与装备产出正确。
- 装备攻击、防御进入战斗计算。
- 礼物偏好和每日限制正确。
- 好感阶段只能合法推进。
- 非法 LLM 指令不会改变状态。

基础设施测试：

- Mobile-Tavern 适配器请求结构。
- SillyTavern 适配器请求结构。
- 提供方自动选择。
- XML 提取与常见错误修复。
- 结构合法但语义非法的动作被拒绝。
- 断线和模型错误能安全降级。

### 11. 美术与 UI 约束

- 当前角色主体画风为年轻幻想动漫风。
- 宿舍使用无武器日常立绘。
- 战斗素材和宿舍立绘分开维护。
- 人物、背景与对话 UI 使用独立层。
- 宿舍对话使用 GAL 式当前对白；历史记录通过“回顾”展开。
- 高频入口位于全宽底栏。
- 新增 UI 时必须检查文字对比度和 16:9 画面遮挡。

### 12. 完成功能的最低验收

每项功能完成前应满足：

- 领域规则有测试。
- 旧存档可以迁移。
- 生产构建通过。
- 在实际浏览器中完成主要交互。
- 控制台无新错误。
- UI 不遮挡底栏、对话框或关键角色信息。
- 外部 LLM 不可用时仍可继续游戏。
