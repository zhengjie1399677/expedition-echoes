# 《远征余响》整体开发指导

> 状态：生效中。任何功能、美术、叙事或重构开始前先阅读本文。  
> 目的：让项目围绕同一套体验与边界演进，避免“单点看似完成、整体又需要重构”。

单日体验的页面职责与落地顺序见 [ONE_DAY_EXPERIENCE_REWORK.md](ONE_DAY_EXPERIENCE_REWORK.md)。

## 1. 项目北极星

《远征余响》是一个以 {{user}} 为非参战队长、以三名队员为核心的二次元幻想小队远征游戏。

玩家应感受到：自己每天都在为队伍做选择；选择会改变远征的资源、风险与人物反应；角色能与队长自由交谈，但游戏事实始终可信。

当前版本优先完成一个有深度的可重复闭环，而不是堆叠页面、角色数量或美术资产：

```text
城镇接取委托
→ 编队与行囊取舍
→ 远征战斗与事件选择
→ 胜利 / 撤退 / 失败结算
→ 宿舍角色反馈
→ 上楼休息至次日
```

## 2. 当前开发优先级

按顺序推进；没有明确理由时，不跨级扩展。

1. 初始三人：职业技能、战斗反馈、压力反应与宿舍互动。
2. 远征深度：行囊、战斗、事件选择、三种结算以及可见后果。
3. 轻量目标框架：传闻、区域威胁、事件钩子和后续任务，不做强制线性主线。
4. 关系内容：好感阶段、状态触发的 LLM 场景、远征后反应和 LLM 上下文。
5. 统一视觉与音效：可读性、动效、按钮状态、暖色奇幻风。
6. 招募角色：仅在前三名角色的美术、战斗和叙事模板成熟后开始。

近期明确不做：新招募入口、新可玩角色、复杂装备耐久、无限随机任务、要求 LLM 才能运行的核心功能。

## 3. 玩家、角色与叙事原则

- {{user}} 是队长，不参战；队员不能替玩家做重大决定。
- 初始可玩角色只有岚、雾、星罗。角色数量不是当前内容目标。
- 主线不是固定章节清单，而是“目标框架 + 可变路径”。玩家可以选择处理顺序、态度或暂时搁置。
- 人物性格、关系阶段和既有事件必须影响对话，但不应把角色写成只会重复人设标签。
- 关键剧情结果由状态条件触发；LLM 只负责表达、反馈和有限建议。

角色的详细设定见 [GAMEPLAY_AND_LLM_DESIGN.md](GAMEPLAY_AND_LLM_DESIGN.md)。

## 4. LLM 与确定性规则的边界

### 游戏代码必须负责

- 金币、经验、生命、压力、补给、装备、掉落和任务完成。
- 事件前置、事件选择、区域状态、奖励档位和结局条件。
- 存档、迁移、数值计算和所有可重复验证的规则。

### LLM 可以负责

- 自由宿舍对话、角色语气和好感阶段表现。
- 由游戏状态触发的角色场景：根据远征结果、压力、事件选择和关系阶段生成当下反应。
- 对远征结果、礼物、传闻和事件选择的叙事反馈。
- 在白名单已有的地点、角色、任务模板中提出线索或建议。

### LLM 绝不能负责

- 直接写入游戏状态，或自行确认“任务完成”。
- 发放未定义的道具、数值、角色或区域。
- 覆盖玩家选择、跳过前置条件、编造已成事实的世界信息。

任何未来结构化输出都必须经过：提取 → 格式校验 → 白名单/语义校验 → 领域 action。解析器不得直接修改状态。

## 5. 系统设计约束

### 5.1 远征

- 城镇背包是长期仓库；远征行囊是本次可带入补给，固定上限为 10 格。
- 食物、绷带、镇定剂占用行囊；装备不占格；战利品在结算时入库。
- 每个事件必须提供至少两种可理解的选择，并明确收益、代价或风险方向。
- 事件选择必须在结算、日志或后续状态中留下可见结果。
- 胜利、撤退、失败都必须清楚展示消耗、返还和收益；不能让玩家猜规则。

### 5.2 压力

- 现有 `morale` 是压力值：0 为平静，数值越高压力越大。
- 受击与冒险探查提高压力；休整与镇定剂降低压力；高压力降低战斗表现。
- 首版不做离队、永久损伤或强制失败。压力用于制造取舍，不用于惩罚玩家。
- 后续 UI、文案和变量命名应逐步统一为“压力”；改名必须带迁移与测试，不能只改显示文字。

### 5.3 经济与成长

- 每个新增资源必须同时说明来源、用途、上限和玩家取舍；只有来源没有消耗的资源不加入。
- 装备数值必须进入领域计算，UI 不得只展示“看起来有加成”的数值。
- 每次升级、装备或事件收益都应有可感知的战斗或管理反馈。

### 5.4 状态触发的 LLM 场景

- 不以大量固定短剧情替代自由对话。固定内容只定义触发条件、已发生事实、可选的队长态度和允许改变的关系标记。
- 进入宿舍时，游戏可根据最近远征结果、压力阶段、事件选择、好感和近期记忆构造“场景上下文”，交给 LLM 生成角色的开场与回应。
- LLM 只能叙述角色反应、提出问题或给出情绪反馈；不能修改远征结果、压力、奖励或替队长作决定。
- LLM 不可用时，使用与同一触发条件对应的简短本地降级台词，核心循环不受影响。

### 5.5 双通道对白与请求预算

- 所有依赖 LLM 的互动都必须同时有两条通道：**固定对白**与**LLM 深聊**。
- 固定对白是游戏内容的一部分：即时、可测试、可在离线时完整使用；它承担任务意见、事件第一反应、关键提示和降级文案。
- LLM 通道只在玩家主动追问、输入自由文本或明确选择“展开讨论”时调用；它承担个性化细节与自然延续，不承担必须阅读的信息。
- 打开任务、进入区域、结算或进入宿舍时，不得自动为三名角色分别请求模型。
- 三人需要共同回应同一件事时，默认显示三条预设短句；若玩家选择“听听大家的想法”，最多使用**一次**合并请求生成短小讨论摘要，或让玩家选择一名角色单独追问。
- 每次 LLM 请求须设置明确的上下文上限与输出上限，并将结果缓存到当前场景，刷新页面不得重复消耗。

### 5.6 战斗特效方向

- 当前 Phaser 仅承担战斗画布、角色表现和基础攻击反馈；现阶段视觉效果克制不是引擎限制。
- 不因为追求特效而迁移到 Pixi.js。Phaser 的 WebGL 渲染足以完成粒子、补间、屏幕震动、闪白、轨迹、命中停顿与镜头推进。
- 后续优先建立可复用的效果层：攻击命中、技能施放、受击、击杀、压力临界与结算；先统一节奏与色彩，再增加复杂滤镜。
- 所有效果必须服务于可读性：玩家应能一眼分辨普通攻击、技能、受击、治疗/减压与战斗结束。

## 6. 架构职责

```text
src/content/         静态内容：角色、任务、敌人、装备、事件模板
src/domain/          纯 TypeScript 模型、规则、reducer、数值计算
src/infrastructure/  存档、资源预加载、LLM 适配与降级
src/ui/              React/Phaser 展示与输入，不计算核心规则
public/assets/       角色、背景和 UI 图像资源
docs/                产品设计、规范和记录
```

- `content` 不读取运行状态、不执行随机逻辑。
- `domain` 不访问 React、DOM、`localStorage`、网络或 LLM。
- `infrastructure` 不决定游戏规则。
- `ui` 只渲染领域结果、派发 action；不能在组件中修改金币、伤害、掉落或事件结果。
- Phaser 只表现战斗，不拥有战斗真相；真相保留在 `domain`。

## 7. 功能实施流程

任何非微小文案修改按以下顺序进行：

1. 在设计文档写清楚玩家目标、输入、结果、失败方式和不做什么。
2. 确认它属于现有优先级，且不会绕开本文的边界。
3. 在 `content` 定义静态内容，在 `domain` 定义模型和 action。
4. 先写或更新领域测试，再接入 reducer 与 UI。
5. 接入 UI 时提供禁用状态、空状态、错误提示和清晰的结果反馈。
6. 新增持久字段时同步处理存档迁移。
7. 运行测试和生产构建；涉及交互或画面时做本地手动检查。
8. 将“已实现 / 规划中”的状态更新到设计文档，避免文档与代码混淆。

不要为了赶进度直接把规则写进 `App.tsx`，也不要用一次性 CSS 覆盖掩盖结构性 UI 问题。

## 8. 状态、存档与迁移

`GameState.version` 是存档契约。新增或变更持久状态时，必须同时：

1. 更新类型与初始状态。
2. 在 `storage.ts` 为旧档提供安全默认值和清洗逻辑。
3. 更新版本范围与旧 key 迁移策略（必要时）。
4. 为旧档、缺字段、非法字段各写一项测试。
5. 确认新字段不会让玩家因旧档卡死。

禁止用“读不到字段就重置整档”替代迁移，除非存档已经无法安全解析。

## 9. UI、美术与可访问性

- 视觉基调：温暖奇幻、羊皮纸、深木、铜金、赭红；避免大面积绿色 UI 底色。
- 人物是年轻、二次元幻想风；宿舍为无武器的日常装，战斗素材与宿舍素材分开维护。
- 新按钮必须有默认、悬停、禁用和键盘焦点状态，文字与背景有足够对比度。
- 任何关键操作都不能被底栏、浮层或背景遮挡；16:9 和较窄窗口都要检查。
- 生成或导入图像前先确认它是否真的补足玩法/氛围，不为填空而增加资产。
- UI 文字显示应使用领域层最终结果，不能复制一套独立计算。

## 10. 测试与验收

领域规则变更必须有对应测试，至少覆盖：

- 正常路径；
- 边界值和资源不足；
- 重复 action 或非法 action；
- 与存档/结算相关的状态回收；
- 新功能不会破坏既有远征、每日循环或装备计算。

功能完成最低标准：

- `npm test` 通过。
- `npm run build` 通过。
- 旧存档可安全载入或有明确迁移。
- 关键操作在本地可走通，控制台无新错误。
- LLM 不可用时，核心流程仍然可玩。
- 文案、按钮、结果反馈和视觉状态与规则一致。

## 11. 提交与重构原则

- 一次提交只解决一个可描述的问题；不要把机制、全面格式化和无关美术改动混在一起。
- 工作区有其他未提交内容时，只修改任务必需的最小范围，不覆盖、不重置他人改动。
- 重构先保留行为，再分文件；若规则改变，必须明确为“玩法改动”并补测试。
- 出现两个以上页面复制同一规则或同一数值时，抽到 `domain`/`content`，不要继续复制。
- 新的“临时方案”必须标注退出条件；没有退出条件的临时方案会变成永久债务。

## 12. 近期里程碑

### M1：可重复远征

三人职业差异、10 格行囊、战斗/事件选择、三种结算、压力反馈完整可玩。

### M2：会回应队长的队伍

远征后宿舍对话、好感阶段、少量个人事件和可控 LLM 上下文。

### M3：轻量世界推进

传闻、区域威胁、事件后果和任务变化构成目标框架；仍允许玩家自由选择。

### M4：内容扩展

在角色美术/行为模板成熟后，逐个制作新的可招募角色与对应完整内容。
