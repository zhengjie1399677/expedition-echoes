## 1. 游戏概述

### 1.1 一句话体验

玩家作为不参战的远征队长 **{{user}}**，在有限的一天里听取队员与城镇的声音，决定队伍为什么事冒险、怎样准备、何时继续或撤退；回到宿舍后，队员记得这一天，并对队长产生新的看法。

### 1.2 北极星

以三名队员为核心、{{user}} 为非参战队长的二次元幻想小队远征游戏。玩家应感受到：**自己每天都在为队伍做选择；选择会改变远征的资源、风险与人物反应；角色能与队长自由交谈，但游戏事实始终可信。**

### 1.3 设计支柱

1. **确定性优先**：游戏代码维护事实与规则；LLM 只负责表达、表演、联想和有限提议，所有提议经白名单校验后才成为游戏行为。无 LLM、请求失败或 iframe 禁止本地存储时，核心游戏仍完整可玩。
2. **深度优先于广度**：先完成一个有深度的可重复闭环，不堆叠页面、角色数量或美术资产。
3. **选择有后果**：每一段体验都要回答——队长现在知道了什么？能做什么有代价的决定？这个决定稍后会在哪里被看见或提起？
4. **自由叙事，非强制主线**：主线是"目标框架 + 可变路径"，由传闻、区域威胁、事件钩子和任务变化构成，而非固定章节清单。

## 2. 玩家、角色与叙事原则

- {{user}} 是队长，不参战；队员不能替玩家做重大决定，可以建议、担忧或反对。
- 初始可玩角色只有**岚、雾、星罗**三人；角色数量不是近期内容目标（招募为后期内容，见 §4.4）。
- 人物性格、关系阶段和既有事件必须影响对话，但角色不应被写成只会重复人设标签。
- 关键剧情结果由明确的状态条件触发，不由模型判定。

## 3. 核心循环

### 3.1 游戏循环（已实现）

```text
新的一天
→ 查看小镇新闻与任务
→ 接取当日唯一任务
→ 编成队伍、装备与准备行囊
→ 远征战斗与事件选择
→ 获得金币、经验、材料与道具
→ 返回城镇
→ 出售、打造、购买礼物、宿舍交流
→ 休息至次日
```

### 3.2 单日体验链（已确认的产品骨架）

```text
晨间：城镇出现变化 / 传闻 / 委托
→ 队长：与队员和酒馆交流，确定今天要回应的问题
→ 准备：编队、行囊、中央广场补给与礼物
→ 出发：处理战斗、压力与风险事件
→ 结算：明确带回什么、失去什么、留下什么后果
→ 夜晚：宿舍中由 LLM 依据真实经历生成角色反应
→ 休息：进入次日，世界与角色保留这一天的痕迹
```

### 3.3 每日决策三问

每个游戏日最少应有三类决策（队长感）：

1. **目标决策**：接哪个委托，或今天暂缓哪一个问题。
2. **风险决策**：带哪些补给、事件中休整还是探查、何时撤退。
3. **关系决策**：回宿舍后安慰、追问、认可或暂时沉默。

### 3.4 每日任务规则（已实现）

- 使用游戏内天数，不依赖现实时间；每天只能正式接取一次任务，接取后当天不可更换。
- 完成、撤退或放弃都消耗当日任务机会；奖励在任务完成后结算。
- 玩家主动选择"休息至次日"后刷新任务板。

## 4. 角色设计

### 4.1 初始三人（已实现，数据见 `src/content/data/heroes.json`）

| 角色 | 职业 | 定位 | 主动技能 | 关键词 | 关系阶段表现 |
| --- | --- | --- | --- | --- | --- |
| 岚 | 先锋 vanguard | 前排坦克，生命与防护高 | 守望号令（降全队压力 8） | 守夜、责任、旧军章、热茶、不要逞强 | 由克制走向主动承担最坏情况 |
| 雾 | 游侠 ranger | 稳定输出，攻击距离 1–2 | 贯风箭（无视距离 +3 伤害） | 地图、风向、小赌、山果、逃跑不是失败 | 由试探走向最先报出真实危险 |
| 星罗 | 术士 mage | 高攻脆皮，距离 2–3 | 星辉爆裂（全体 6 伤害） | 星图、笔记、封印、甜食、再看一眼 | 由好奇走向学会接受"先撤退" |

三人初始关系：岚压住雾的冒险提议但也承认其直觉；雾逗星罗但在她研究时替她放哨；星罗尊敬岚的稳定并温和指出他责任过载。{{user}} 是三人共同承认的队长。

### 4.2 好感与关系阶段（已实现，阈值 0/20/50/80）

| 阶段 | 人设表现 |
| --- | --- |
| 陌生 | 礼貌、克制、保持距离 |
| 熟悉 | 分享习惯、日常看法和轻量过去 |
| 信赖 | 谈论目标、恐惧、创伤和重要选择 |
| 羁绊 | 专属事件、更主动的关心与情感表达 |

- 关系阶段必须进入 LLM 提示上下文，改变称呼、语气、主动程度与可透露信息，而非替换固定台词。
- 好感不能只靠无限赠礼：每日/每次远征后限制有效赠礼次数；关键阶段必须完成个人事件才能突破。

### 4.3 角色反馈（已实现）

- 任务详情默认展示三人各一句**固定意见**（即时、离线可用，不触发 LLM）。
- 远征结算提供 `victory / retreat / defeated / idle` 四条预设反应。
- LLM 场景包：已发生事实 + 角色状态 + 队长状态 + 场景目的 → 生成角色开场与回应；不可用时用同触发条件的本地降级台词。

### 4.4 招募（规划中，M4 后）

- 近期**不做**：新招募入口、招募货币、新可玩角色。
- 前提：前三名角色的美术、战斗、叙事模板成熟后，以一个角色为单位完整制作（立绘、宿舍姿态、战斗素材、人格、装备适配、关系事件、测试）。

## 5. 战斗系统

### 5.1 基础规则（已实现）

- 回合制节奏：**玩家行动 → 敌人行动**，非实时。
- 站位：三人队伍分前后排，可换位；攻击距离决定谁能打谁（先锋 1、游侠 1–2、术士 2–3 且不能打贴身）。
- 装备攻击/防御加成进入领域层确定性计算（`equipmentBonuses` → `attackDamage`）。
- 敌人特质（已实现）：pack 群狼、thorns 荆棘、spores 孢子、rock-armor 岩甲、ancient-core 古核。

### 5.2 职业被动（已实现，`domain/combat.ts`）

| 职业 | 被动 | 效果 |
| --- | --- | --- |
| 先锋 | 坚守 | 前排时受伤降低，对贴身敌人有反制 |
| 游侠 | 锐眼 | 后排时提升命中与暴击，可优先攻击远程敌人 |
| 术士 | 共鸣 | 同排有队友时强化法术伤害，单独站位减弱 |

被动效果必须进入领域确定性计算；UI 只显示被动摘要。

### 5.3 技能（已实现）

`skillDefinitions`：守望号令 / 贯风箭 / 星辉爆裂（已用）+ 治愈之光 / 钢铁意志（医师向预留）。技能类型：`morale_recovery | single_damage | all_damage | heal_single`。

### 5.4 敌人意图系统（已实施，定稿见 §16 战斗意图系统）

✅ **A1 已实施（v13）**：`domain/intents.ts`（rollIntent / resolveEnemyAction / targetForIntent / intentDescription / chargeMultiplier）、8 敌人意图池进 enemies.json、战斗时序改造（玩家攻击 guard 减半、单目标技能/火焰瓶同规则、敌人按意图行动后重 roll）、UI 敌人卡片意图展示（含蓄力重击 ×2 提示）、26 个意图测试。

| 意图 | 兑现行为 | 玩家决策 |
| --- | --- | --- |
| attack | 按 targetHint 选目标造成伤害 | 常规处理 |
| charge | 本回合不攻击，蓄力层数 +1（上限 2 层 = 伤害 ×2） | 集火打掉或换血硬吃 |
| guard | 本回合不攻击，该意图生效期间受伤减半 | 先处理其他目标 |
| pressure | 对目标施加压力，不放血 | 优先击杀或准备镇定剂 |

规则：意图池数据驱动 + 注入 RNG；连续两次不得相同；charge 兑现后强制 attack；无配置回退 attack；UI 只读展示。

### 5.5 压力系统（已实现，术语已统一）

- 0 为平静，数值越高压力越大；受击与冒险探查提高，休整与镇定剂降低；高压力降低战斗表现（当前实现为降低攻击）。
- 首版**不做**恐慌、离队或永久惩罚——压力用于制造取舍，不用于惩罚。
- ✅ **术语已统一（v13）**：代码/UI/JSON 全链路 `morale` → `pressure`，旧档自动迁移；不同角色的压力反应文本后续补充。

## 6. 远征与资源

### 6.1 远征流程（已实现）

```text
任务板接取 → 编成队伍 → 准备行囊 → 进入节点序列（战斗/事件交替） → 胜利/撤退/失败结算
```

- 节点序列数据驱动（`expeditionNodes` / `forestExpeditionNodes`），当前两条线路：
  - 遗迹线 7 节点：坍塌入口 → 废弃补给室 → 回声长廊 → 旧日营火 → **坍塌通道（risk_fight）** → **游商帐篷（bargain）** → 封印门厅
  - 林地线 7 节点：林缘古道 → 临时营地 → 孢子林径 → **药草丛（aid_hero）** → 暮色营火 → **回声陷阱（track+pressureCost）** → 古树圣所
- ✅ **A2 已实施**：事件 schema 扩展（`risk_fight/aid_hero/bargain` 效果 + title/once/pressureCost 参数）、4 个新事件（坍塌通道/药草丛/游商帐篷/回声陷阱）、一次性事件 seenEvents 规则、risk_fight 触发额外战斗、bargain 双向交易、6 个事件测试。
- 事件每个必须提供至少两种可理解选择，并在结算、日志或后续状态留下可见结果。
- 胜利、撤退、失败必须清楚展示消耗、返还与收益。

### 6.2 行囊与补给（已实现）

- 城镇背包是长期仓库；**远征行囊**固定上限 **10 格**，限制本次可带入补给。
- 食物、绷带、镇定剂、火焰瓶、铁壁药丸占行囊；已装备不占格；材料/礼物默认不可带入。
- 副本战利品先记入本次收益，结算统一入库，不因行囊满而丢失。

### 6.3 食物（已实现）

- 每进入一个副本节点全队消耗一份食物；跨日消耗城镇基础食物。
- 食物不足仍允许前进（避免死档），饥饿造成生命/疲劳/攻击/防御/士气方面的惩罚。
- 料理分档：普通干粮补基础食物；优良少量恢复；稀有下节点增益；史诗/传说用于特殊事件，不作日常必需。

## 7. 经济、打造与成长

### 7.1 品质与颜色（已实现，统一五档）

| 品质 | 颜色 | 用途 |
| --- | --- | --- |
| 普通 | 灰 | 基础材料、普通食物、常见装备 |
| 优良 | 绿 | 稳定的初级强化资源 |
| 稀有 | 蓝 | 明显用途差异的装备或料理 |
| 史诗 | 紫 | 特殊配方、角色偏好礼物或事件奖励 |
| 传说 | 金 | 稀有事件、任务链终点或收藏内容 |

### 7.2 材料（已实现）

- 当前两种：遗迹碎片、锈铁块；出售价按稀有度递增（0:1 / 1:5 / 2:30 / 3:150 / 4:1000）。
- 材料三重去向：出售换金币 / 保留打造 / 作为任务或事件条件 → 形成实际取舍。

### 7.3 打造（已实现，20 配方）

- 配方 = 材料 + 金币 → 装备入背包；装备直接进入战斗计算。
- 当前覆盖三职业武器/护甲/饰品 × 普通·优良·稀有三档。
- 近期不做：复杂耐久、套装、职业限制外的扩张。

### 7.4 市场（已实现）

- 中央广场固定售价：武器 36–40、防具 38–42、饰品 32、礼物 5–40、战斗消耗品 15–18。
- 打造从底栏移除，未来进入中央广场铁匠铺场景内功能（重排中）。

### 7.5 成长反馈（已实现）

- 升级：`maxHp +5`、基础攻击 `+2`、经验需求按等级递增。
- 装备分档明显；装备加成必须进入领域计算并有回归测试。

## 8. LLM 叙事系统与职责边界

### 8.1 职责划分（已确认，代码维护事实）

| 层 | 职责 |
| --- | --- |
| 游戏代码 | 金币、经验、生命、压力、补给、装备、掉落、任务完成、事件前置、区域状态、奖励档位、结局条件、存档迁移 |
| LLM 可做 | 自由对话、好感阶段人设、礼物反馈、任务结果评论、角色记忆、每日新闻/趣事/传闻、白名单模板内提议任务、串联事件线索 |
| LLM 禁做 | 修改金币/经验/好感/属性、创建任意装备数值、决定未验证掉率、跳过前置、生成不存在的地点/NPC/敌人后直接执行、直接写入游戏状态 |

### 8.2 双通道对白（已确认）

- 所有依赖 LLM 的互动必须同时有**固定对白**与 **LLM 深聊**两条通道。
- 固定对白：即时、可测试、离线可用；承担任务意见、事件第一反应、关键提示和降级文案。
- LLM 通道只在玩家主动追问/自由输入/明确选择"展开讨论"时调用。
- 三人共同回应同一事：默认三条预设短句；"听听大家的想法"最多一次合并请求；请求结果缓存到当前场景，刷新不重复消耗。

### 8.3 结构化叙事协议（设计中）

- 三级策略：原生结构化输出 → 普通文本 + XML 信封 → 叙事降级（只保留安全文本/本地模板）。
- 处理链：提取信封 → 清除围栏 → 有限格式修复 → XML 解析 → 版本/标签/长度/枚举校验 → 白名单语义校验（任务模板、地点、敌人、NPC、奖励档位、事件状态）→ 合法动作经 reducer 应用。
- 解析器不得直接修改状态；完全失败用本地模板。即使原生结构化输出也仍需语义校验。

### 8.4 请求预算

打开任务/进入区域/结算/进宿舍不得自动为三人分别请求模型；LLM 请求须设上下文与输出上限。

## 9. 每日新闻与事件导演（已实施基础版，LLM 增强规划中）

### 9.0 实施状态

## 16. 战斗意图系统（原 COMBAT_INTENT_SYSTEM.md，已定稿）

> 状态：**设计定稿**，可进入实施。  
> 目的：为《远征余响》引入"敌人威胁预告"，让战斗从"数值对撞"变成"读题→解题"。  
> 关联：PROJECT_DEVELOPMENT_GUIDE §15（历史技术参考）；GDD §19.13.2（战斗深度）；GDD §5.4。  
> 术语：本文统一使用"压力"（代码字段 `pressure`，v13 起取代旧 `morale`）。

---

### 1. 问题（不变）

当前战斗是"玩家行动 → 敌人立即反击"的即时结算制（`combat.ts` 的 `ATTACK` case 内 `survivingAttackers` 循环）：

- 敌人没有"下一回合要做什么"的概念，玩家**无法预判威胁**；
- 站位、集火、道具使用都缺乏决策依据，战斗退化为"血多就赢"的数值对撞；
- 已实现的敌人特质（pack / thorns / spores / rock-armor / ancient-core）只有被动效果，没有主动威胁节奏。

### 2. 目标（不变）

在不改变现有"玩家行动 → 敌人行动"节奏、不改回合制架构的前提下：

1. 每个敌人行动前，向玩家**预告其下一次行动**（意图）；
2. 敌人行动按**意图执行**，而非统一反击；
3. 意图从**数据驱动**的意图池中按规则选择，确定性、可测试；
4. 新威胁节奏产生决策点：集火蓄力目标、避开防御目标、保护被瞄准的后排。

### 3. 设计边界（沿用项目纪律，含压力术语）

- 意图只存在于 `domain` 层；UI 只读展示，不计算。
- 无意图字段的敌人按纯 `attack` 处理（向后兼容，不影响现有测试与存档）。
- 数值一律进 `BALANCE` 或 enemies.json 数据文件，不硬编码。
- 意图选择使用**可注入 RNG**（`Rng = () => number`），测试可复现。
- 压力相关数值使用 `pressure*` 命名（v13 已统一），不出现 `morale`。

### 4. 数据结构（定稿）

```ts
// src/domain/model.ts
export type EnemyIntentType = 'attack' | 'charge' | 'guard' | 'pressure';

export interface EnemyIntent {
  type: EnemyIntentType;
  targetHint?: 'front' | 'back' | 'weakest'; // 缺省 front
  damage?: number;    // 覆盖默认伤害（charge 的下一回合倍率见 §5）
  pressure?: number;  // pressure 意图施加的额外压力
}

export interface Enemy {
  // ...现有字段
  intents?: EnemyIntent[]; // 意图池；缺省视为 [{ type: 'attack' }]
}

export interface Expedition {
  // ...现有字段
  enemyIntents: Record<string, EnemyIntent>;   // enemyId -> 当前预告的意图
  enemyCharge: Record<string, number>;          // enemyId -> 蓄力层数（charge 意图积累）
}
```

### 5. 意图语义（回合是"预告→玩家行动→敌人兑现"）

| 意图 | 敌人兑现时行为 | 玩家看到预告后的决策 |
|---|---|---|
| `attack` | 按 `targetHint` 选目标，造成 `damage × chargeMultiplier` 伤害并消耗蓄力 | 常规处理 |
| `charge` | 本回合不攻击，`enemyCharge[id] += 1`（最多 2 层，即伤害 ×2 封顶） | **下回合必吃大招**——要么集火打掉，要么换血硬吃 |
| `guard` | 本回合不攻击；该意图生效期间受到玩家伤害减半 | **这回合打它亏**——先处理其他目标 |
| `pressure` | 对目标施加 `pressure` 点压力，不放血 | 优先击杀或准备镇定剂 |

蓄力伤害公式（覆盖默认伤害时）：

```text
实际伤害 = (intent.damage ?? enemy.damage) × (1 + enemyCharge - 1)
         = (intent.damage ?? enemy.damage) × enemyCharge（charge 层数从 1 起，封顶 2）
```

目标倾向：

| `targetHint` | 选择规则 |
|---|---|
| `front`（缺省） | 现有逻辑：从前排起第一个可攻击的存活英雄 |
| `back` | 从后排起第一个可攻击的存活英雄（威胁游侠/术士） |
| `weakest` | 当前 `hp / maxHp` 最小的存活英雄 |

### 6. 意图选择规则（rollIntent，定稿）

- 从 `enemy.intents` 池中随机选择；
- **连续两次不得相同**（避免重复无趣）；
- `charge` 意图兑现后，下一回合强制 `attack`（蓄力必然导致攻击，且防止无限蓄力）；
- 意图池为空或未配置 → 回退 `attack`；
- 选择算法只接受 `Rng` 注入，默认 `Math.random`。

```ts
// src/domain/intents.ts（新模块）
export type Rng = () => number;

export function rollIntent(
  enemy: Enemy,
  currentIntent: EnemyIntent | undefined,
  charge: number,
  rng: Rng = Math.random,
): EnemyIntent;

export function targetForIntent(
  party: Hero[],
  intent: EnemyIntent,
): Hero | undefined;

export function resolveEnemyAction(
  state: GameState,
  attacker: Enemy,
  intent: EnemyIntent,
): GameState;

export function intentDescription(intent: EnemyIntent, enemyName: string): string;
```

`rollIntent` 语义：

1. `intents` 未配置或为空 → 返回 `{ type: 'attack' }`。
2. `charge > 0`（上一回合蓄力未兑现）→ 强制返回 `attack`（兑现蓄力）。
3. 从池中按 `rng` 均匀抽取；若结果与 `currentIntent` 相同，再次抽取（最多 3 次尝试，仍相同则接受）。
4. 返回抽取结果。

### 7. 战斗时序改造（最小侵入，定稿）

```text
遭遇开始（START_EXPEDITION / 进入 combat 节点）
  → 对每个敌人 rollIntent 并写入 expedition.enemyIntents  ← 预告可见
  → 玩家行动（ATTACK / USE_SKILL / 道具 / 站位调整）
       ├─ 玩家攻击敌人时：若该敌人当前意图为 guard → 伤害减半
       └─ 敌人全灭 → 结算，结束
  → 存活敌人按各自 enemyIntents 兑现行动（resolveEnemyAction）
       ├─ attack  → 原反击逻辑按 targetHint 选目标，伤害 × charge 倍率，charge 清零
       ├─ charge  → 只累积 enemyCharge，log「正在蓄力」
       ├─ guard   → 只 log「架起防御」
       └─ pressure→ 目标压力 + pressure 值
  → 存活检查（全灭 → settleExpedition('defeated')）
  → 对存活敌人重新 rollIntent，覆盖 enemyIntents  ← 新一轮预告
  → 回到「玩家行动」
```

现有 `ATTACK` case 中 `survivingAttackers` 循环体，替换为 `resolveEnemyAction(state, attacker)`；玩家伤害结算处增加 guard 减半判断。先锋「坚守」反制、pack/rock-armor 等既有加成**保留不变**，与意图叠加。

**关键细节（与既有系统交互）**：

- **guard 减半**：只对"玩家对处于 guard 意图的敌人造成的伤害"生效（普通攻击、单目标技能、火焰瓶）。范围技能（星辉爆裂）不减半，保持简单。
- **压力意图与压力系统联动**：`pressure` 意图施加的压力走 `editHero` 的 `pressure` 字段，受 `settings.pressureEnabled` 开关控制（关闭时忽略）。
- **敌人行动顺序**：`resolveEnemyAction` 按 `state.expedition.enemies` 数组顺序执行（与现有反击循环一致），每个敌人独立兑现自己的意图。
- **charge 兑现与死亡**：蓄力中的敌人被击杀后，其 `enemyCharge` 与 `enemyIntents` 条目一并清除（`enemyCharge` 无残留）。
- **站位调整（SWAP）不重 roll**：同一遭遇中玩家换位不改变已预告的意图，避免玩家通过换位"洗牌"。

### 第一部分：事件模板库（G1）

### 1. 现状与问题

- 当前事件仅 2 个模板：`supply-room`（补给室）、`old-campfire`（旧营火），效果组合只有 `recover / scavenge / track` 三种。
- 问题：远征中每两节点一个事件，2 个模板 × 2 条线路 ≈ 玩家第 2–3 天就会看到完全相同的选择和文案，重复感强。
- 目标：定义**事件 schema**（效果白名单、条件、奖励档位），先扩 4–6 个新事件，每种效果组合对应一个不同的叙事犹豫。

### 2. 事件数据结构（定稿）

```ts
// src/domain/model.ts 扩展
export type ExpeditionEventEffect =
  | 'recover'      // 全队恢复 HP + 降压力（休整）
  | 'scavenge'     // 获得材料，压力上升
  | 'track'        // 获得金币，压力上升
  | 'risk_fight'   // 可选的额外战斗：胜利得稀有材料，失败压力大
  | 'aid_hero'     // 指定角色 HP 大幅恢复，其他角色压力略升
  | 'bargain';     // 以材料/金币换取某奖励或情报（双向选择）

export interface ExpeditionEventChoice {
  id: string;
  label: string;
  description: string;
  effect: ExpeditionEventEffect;
  // 效果参数（可选，缺省用 BALANCE 默认值）
  pressureCost?: number;   // 该选择施加的压力
  hpGain?: number;         // 该选择恢复的 HP（用于 aid_hero 单角色）
  goldGain?: number;       // track/bargain 的金币
  material?: { typeId: string; rarity: Rarity; count: number };
  requirement?: string;    // 前置条件描述（如"需要火焰瓶"）
}

export interface ExpeditionEvent {
  id: string;
  title: string;          // 事件标题（当前仅有 prompt，补 title 用于 UI 层级）
  prompt: string;
  background?: string;    // 事件专属背景图（可选）
  choices: ExpeditionEventChoice[];
  once?: boolean;         // 是否为一次性事件（同一远征不重复出现）
}
```

### 3. 事件模板库（第一版 6 个事件）

| 事件 ID | 标题 | 场景 | 选择（效果） | 设计意图 |
| --- | --- | --- | --- | --- |
| supply-room | 废弃补给室 | 封存药箱可用，深处有未触碰箱柜 | 整理伤口(recover) / 翻找药箱(scavenge) | 现有：安全 vs 收获 |
| old-campfire | 旧日营火 | 新鲜足迹通向阴影小径 | 围火休整(recover) / 循迹探查(track) | 现有：安全 vs 情报 |
| **collapsed-passage** | 坍塌通道 | 通道塌方，绕路多耗食物，清障有风险 | 清理碎石(risk_fight) / 绕路前行(recover, 消耗食物) | 新：战斗风险换稀有掉落 |
| **herb-grove** | 药草丛 | 稀有药草被孢兽看守 | 谨慎采摘(aid_hero, 指定最弱角色) / 全部带走(scavenge, 压力+大) | 新：单角色治疗 vs 团队收益 |
| **traveling-merchant** | 游商帐篷 | 商人愿以物易物 | 用材料换金币(bargain) / 用金币买材料(bargain) / 离开(无效果) | 新：经济取舍 |
| **echo-trap** | 回声陷阱 | 符文机关，触发会惊动守卫 | 解除机关(recover, 需镇静剂) / 硬闯(scavenge, 压力+大) / 标记路线(track) | 新：消耗品决策 + 三类收益 |

#### 事件效果与 BALANCE 参数建议

| 效果 | 默认参数 | 说明 |
| --- | --- | --- |
| recover | HP +5、压力 -12 | 沿用 restNode 参数 |
| scavenge | 材料 ×1（普通）、压力 +8 | 沿用 |
| track | 金币 +12、压力 +10 | 沿用 |
| risk_fight | 触发一场额外遭遇（固定敌人 1–2 只），胜利掉落稀有材料 | 走现有 combat 节点流程，新增"奖励+稀有材料"的结算变体 |
| aid_hero | 指定 HP 最低角色 +12 HP、其他角色压力 +4 | 需 `targetHero` 逻辑 |
| bargain | 金币 ↔ 材料双向 | 复用 economy 的 sell/buy 逻辑 |

### 4. 事件选择规则（定稿）

1. 事件不重复：同一次远征中，`once: true` 的事件只出现一次（用 `Expedition.seenEvents: string[]` 记录，v13 后新增字段需存档迁移）。
2. 选择必须有可见后果：写入 `state.log`、结算摘要或后续事件条件（沿用现有约束）。
3. 效果参数进数据文件，不硬编码；新效果类型必须先扩展 `ExpeditionEventEffect` 联合类型再实现 reducer 分支。
4. 事件文案支持 `{{user}}` 与角色名占位；LLM 场景包不替代事件选择本身。

### 第二部分：区域威胁框架（G2）

### 5. 现状与问题

- 任务板 4 张卡片互不相关，像是随机刷新的独立委托，而非同一个世界的不同切面。
- "区域威胁"在 GDD/PROJECT_DEVELOPMENT_GUIDE 中被多次提及（M3 轻量世界推进），但无任何具体设计。
- 目标：建立"**区域 + 威胁等级 + 事件后果**"模型，让任务板、传闻、远征事件与次日新闻围绕同一世界状态运转，且**不要求线性主线**。

### 6. 区域模型（定稿）

```ts
// src/domain/model.ts 扩展
export type RegionId = 'border-ruins' | 'ash-forest' | 'north-canal' | 'sealed-gate';

export type ThreatLevel = 0 | 1 | 2 | 3; // 0 平静 / 1 异动 / 2 危险 / 3 失控

export interface Region {
  id: RegionId;
  name: string;
  threat: ThreatLevel;
  description: string;         // 区域一句话状态（供传闻/新闻使用）
  missions: string[];          // 属于该区域的任务 ID（任务板按区域分组）
  escalationTo?: RegionId;     // 威胁升级后的相邻区域（事件链延续）
  unlockAtDay?: number;        // 第几天开放（可选，默认 day 1 全开放）
  unlockThreat?: ThreatLevel;  // 需要其他区域威胁达到的等级（可选）
}
```

`GameState` 增加 `regions: Record<RegionId, ThreatLevel>`（v13 后新增持久字段，需存档迁移默认全 0）。

### 7. 四个区域的初始设计

| 区域 | 当前威胁 | 描述 | 关联任务 |
| --- | --- | --- | --- |
| 边境遗迹 border-ruins | 2（异动） | 遗迹道路异响影响商路；这是第一条事件线的舞台 | border-echoes、sealed-gate |
| 灰烬林地 ash-forest | 1（异动） | 林地异变从古树圣所向外扩散 | forest-disturbance |
| 北侧水渠 north-canal | 0（平静） | 水渠怪声传闻；预留后续事件链入口 | （预留） |
| 封印门厅 sealed-gate | 2（危险） | 连续回声，封印正在回应什么 | rusted-patrol |

### 8. 威胁等级语义与推进规则

| 威胁 | 表现 | 触发方式 |
| --- | --- | --- |
| 0 平静 | 无传闻；任务板少 1 个该区域委托 | 该区域事件链完成或自然消退 |
| 1 异动 | 城镇传闻出现；任务板出现该区域委托 | 每日新闻生成器按时间/事件推进 |
| 2 危险 | 任务难度上升（敌人波次增强）；酒馆警告文案 | 玩家在该区域失败/撤退/特定事件选择 |
| 3 失控 | 该区域任务消失，改为"紧急平息"委托；次日新闻引用 | 威胁 2 时连续两次失败 |

**核心规则**：

1. **只升级不强制**：威胁升级由玩家行为 + 事件结果触发（确定性规则），LLM 只建议不决定。
2. **不锁内容**：区域不因威胁等级封锁，玩家随时可以挑战更高威胁区域（风险自担），避免"强制线性"。
3. **任务板分组**：任务按区域展示，同一区域的委托是该区域问题的不同处理方式（呼应 GDD §18.6"同一问题的不同切面"）。
4. **后果可见**：威胁升级/降级必须出现在次日新闻、酒馆文案或任务板描述中，让玩家能认出"世界记得我的选择"。
5. **平衡**：威胁等级不直接改数值，而是改敌人波次配置（每个任务提供 `threatWaves: Record<ThreatLevel, enemyWaves>`，缺省沿用默认波次）——避免数值膨胀，只改内容。

### 9. 与 LLM / 每日新闻的配合

- 每日新闻生成器输入增加：`regions` 威胁快照。
- 输出新闻时优先引用威胁 ≥2 的区域；传闻绑定区域（`<action type="offer_quest" region="border-ruins">`）。
- LLM 可以提议"某个区域威胁升级"，但必须经过白名单校验（区域 ID 存在、升级条件满足），升级本身由代码执行。

### 10. 实施顺序（建议）

**事件模板库**：

1. `model.ts` 扩展 `ExpeditionEventEffect` 与 `ExpeditionEvent`（title/once/参数）。
2. 新增 4 个事件（collapsed-passage、herb-grove、traveling-merchant、echo-trap）到 `gameContent.ts`，按线路插入节点序列。
3. `expedition.ts` 的 `RESOLVE_EVENT` 补 `risk_fight / aid_hero / bargain` 分支。
4. `Expedition.seenEvents` 字段 + 存档迁移（v13→14，若实施在 v13 之后）。
5. 补事件测试：每种效果、一次性规则、非法选择。

**区域威胁**：

1. `model.ts` 加 `Region` 类型与 `regions` 状态；`createInitialGame` 初始化 4 区域。
2. `gameContent.ts` 定义 `regions` 静态数据（含任务分组）。
3. 任务板按区域分组渲染；任务配置 `threatWaves`。
4. 威胁升级规则进 `domain`（如 `escalateRegion(state, regionId)` reducer action），触发点：任务失败/撤退/特定事件。
5. 每日新闻生成器读取威胁快照（与 LLM 协议 §9 联调）。
6. 存档迁移 + 测试。

### 11. 验收标准

1. 新玩家第 2 天能在任务板看到按区域分组的委托，并能从传闻认出昨天的选择影响。
2. 远征中事件选择不重复（同一远征内 `once` 事件只出现一次）。
3. 威胁升级后：任务波次变化、次日新闻引用、酒馆文案变化，三处至少两处可见。
4. 无 LLM 环境：事件、区域、威胁升级全部可玩、可测、确定性。
5. `npm test` 全绿、`npm run build` 通过、旧存档安全迁移。

### 12. 明确不做（本期范围外）

- 不做强制线性章节/日期解锁主线（区域可随时挑战）。
- 不做事件分支结局系统（事件后果只进状态与新闻，不做多重结局树）。

## 18. 单日体验重构纲要（原 ONE_DAY_EXPERIENCE_REWORK.md）

> 状态：下一阶段产品骨架。后续功能、美术和页面调整以本文为判断标准。  
> 目标：让现有系统不再像并列的页面集合，而是围绕“队长带队度过一天”形成连续体验。

### 1. 一句话体验

玩家作为 {{user}}，在有限的一天里听取队员与城镇的声音，决定队伍要为什么事冒险、怎样准备、何时继续或撤退；回到宿舍后，队员会记得这一天并对队长产生新的看法。

### 2. 每日体验链

```text
晨间：城镇出现变化 / 传闻 / 委托
→ 队长：与队员和酒馆交流，确定今天要回应的问题
→ 准备：编队、行囊、中央广场补给与礼物
→ 出发：在远征中处理战斗、压力和风险事件
→ 结算：明确带回什么、失去了什么、留下什么后果
→ 夜晚：宿舍中由 LLM 依据真实经历生成角色反应
→ 休息：进入次日，世界与角色保留这一天的痕迹
```

每一段都必须回答三个问题：

1. 队长现在知道了什么？
2. 队长现在能做什么有代价的决定？
3. 这个决定稍后会在哪里被看见或被角色提起？

如果一个功能无法回答其中至少一项，它不应进入近期版本。

### 3. 区域职责与页面重组

| 区域 | 玩家目的 | 必须出现的信息/决定 | 应弱化或移除的感觉 |
| --- | --- | --- | --- |
| 城镇 | 看到今天发生什么 | 一条明确传闻或变化；进入酒馆、广场、宿舍、城门 | 单纯“地图菜单” |
| 酒馆 | 明白今天为何出发 | 委托、队员简短意见、任务风险 | 仅作为任务列表与招募页 |
| 中央广场 | 为决定付出资源 | 装备、饰品、礼物购买；以后可放铁匠 | 突兀弹出的商店面板 |
| 队伍管理 | 制定作战方案 | 三人站位、装备、远征行囊 | 与出发流程脱节的独立后台 |
| 城门/远征 | 承担决定的后果 | 战斗、压力、事件、撤退 | 没有叙事含义的重复关卡 |
| 宿舍 | 让一天沉淀为关系 | LLM 场景上下文、礼物、对话、休息 | 纯聊天窗口或数值赠礼页 |

#### 导航原则

- 底栏保留“城镇、队伍、角色、背包”四个高频管理入口；打造不在底栏出现。
- “打造”未来是中央广场铁匠铺的场景内功能，而不是第五个后台页。
- 酒馆、广场、宿舍、城门均优先通过城镇场景进入；底栏不复制这些空间入口。
- 页面切换应被视为进入区域：有短暂镜头推进/淡入、明确环境图和返回路径。

### 4. 队长感：必须贯穿的决定

队长不参战，但不能只是点击下一步。每个游戏日最少应有三类决策：

1. **目标决策**：接哪个委托，或者今天暂缓哪一个问题。
2. **风险决策**：带哪些补给、在远征事件中休整还是探查、何时撤退。
3. **关系决策**：回到宿舍后安慰、追问、认可或暂时沉默。

系统不替 {{user}} 定义动机；队员可以建议、担忧或反对，但最终决定始终由队长表达。

### 5. LLM 场景机制

不预写大量固定短剧情，也不允许模型决定事实。每次需要角色反应时，构造一个有限的场景包：

```text
已发生事实：任务结果、事件选择、获得/损失、压力变化
角色状态：该角色压力、好感阶段、人物性格、近期记忆
队长状态：本日做过的关键选择
场景目的：庆祝 / 安慰 / 追问 / 分歧 / 安静陪伴
允许输出：角色开场、自然对白、提出问题、情绪反应
禁止输出：改写结果、发放奖励、代替队长决定、编造未发生事实
```

LLM 不可用时，使用同一场景包对应的简短本地台词。降级版本必须保留“角色记得这一天”的信息，而不是泛用晚安。

#### 任务意见的双通道示例

任务详情默认展示岚、雾、星罗各一句固定意见：这三句应在页面打开时立即出现，不请求 LLM。玩家随后可以：

- 直接接取或返回；
- 点击某一名角色的“追问”，只请求该角色一次；
- 点击“听听大家的想法”，以一次合并 LLM 请求得到短小讨论，不逐个请求三次。

这样任务信息和角色立场始终即时可读，LLM 消耗由玩家主动选择，而不是由页面加载隐式触发。

### 6. 第一条可玩的事件线

暂不做传统主线章节，先用一个可变目标框架验证体验：**边境遗迹的回声。**

- 城镇传闻：遗迹道路的异响正在影响商路。
- 酒馆委托：不同任务是对同一问题的不同处理方式，而非三张互不相关的卡片。
- 远征事件：补给室、旧营火等选择决定队伍以谨慎、冒险或撤退的方式面对风险。
- 宿舍反馈：岚关心是否安全归来；雾关注路线与后路；星罗关注回声的线索。
- 次日变化：新闻、酒馆文案或下一份委托提及前一天的处理结果。

首版不要求复杂分支结局；只要求玩家在第二天能认出“昨天的选择确实被世界记住”。

### 7. 现有内容的处理

#### 保留并加强

- 三人队伍、站位、行囊、压力、主动技能。
- 远征胜利/撤退/失败结算。
- 中央广场场景、酒馆、宿舍和城门。
- 自由对话与本地降级。

#### 暂停扩展

- 新角色与招募内容。
- 新材料层级、复杂打造、耐久、套装。
- 大量独立地图和无关联任务。
- 用更多 UI 选项代替真正的后果。

#### 需要重排

- 打造从底栏移到未来铁匠铺。
- 队伍管理在“出发整备”时也能被访问，避免玩家在不同页面来回找功能。
- 商店与礼物通过广场摊位呈现，商品面板仅在点击摊位后出现。

### 8. 落地顺序

#### 第一步：让一天有开头和结尾

1. 每日传闻/委托加入“昨天后果”占位。
2. 酒馆任务详情加入队员的一句不同意见。
3. 结算把关键选择压缩成可供宿舍读取的事实摘要。
4. 宿舍 LLM 使用场景包生成开场；离线时使用对应降级台词。

#### 第二步：让空间连续

1. 城镇 → 酒馆 / 广场 / 宿舍 / 城门的进入过渡统一。
2. 广场、酒馆、宿舍各有一个可互动的环境层，不只是背景加按钮。
3. 队伍整备从城门可直接进入和返回。

#### 第三步：让选择有后果

1. 远征事件把选择记录为状态摘要。
2. 下一日传闻、任务条件或角色对话至少引用其中一项。
3. 验证胜利、撤退、失败各有不同的情绪与世界反馈。

### 9. 验收标准

完成第一轮重构后，一名新玩家应能回答：

- “我今天为什么出发？”
- “我为此做了什么准备和取舍？”
- “我在远征中做了什么重要选择？”
- “队员如何看待我的选择？”
- “明天有什么因为今天而不同？”

其中任一问题无法从游戏中自然回答，就说明体验链仍然断裂，优先修复链路而不是添加新功能。

## 19. 玩法与 LLM 叙事设计（原 GAMEPLAY_AND_LLM_DESIGN.md）

> 状态：设计草案  
> 用途：记录当前已经达成共识的游戏循环、成长系统和 LLM 职责边界。  
> 注意：本文同时包含已实现功能与规划功能，具体状态以各节标注为准。

### 1. 核心体验

游戏的核心循环为：

```text
新的一天
→ 查看小镇新闻与任务
→ 接取当日唯一任务
→ 编成队伍、装备与准备补给
→ 远征战斗和事件
→ 获得金币、经验、材料与道具
→ 返回城镇
→ 出售、打造、购买礼物、宿舍交流
→ 结束当天
```

目标不是无限增加系统，而是先完成一个可重复体验的小闭环：

```text
接任务 → 准备 → 远征 → 结算 → 成长 → 角色反馈
```

### 2. 当前已实现

- 城镇、酒馆、宿舍、设置与远征页面。
- 三人队伍编成与前后排换位。
- 背包和角色装备管理。
- 装备攻击加成与伤害减免已进入实际战斗计算。
- 角色等级与经验。
- 多节点远征、敌人选择、撤退与通关结算。
- 宿舍独立房间、日常立绘和 GAL 式对话界面。
- 玩家自由输入、对话回顾与最近上下文。
- Mobile-Tavern 和 SillyTavern 两种聊天适配器。
- 无可用 LLM 时的本地对白降级。

### 3. 任务与每日循环

#### 3.1 每日任务

- 使用游戏内天数，不依赖现实时间。
- 每天只能正式接取一次任务。
- 任务接取后当天不可随意更换。
- 完成、撤退或放弃都会消耗当天的任务机会。
- 奖励在任务完成后结算，不在点击接取时立即发放。
- 玩家主动选择“休息至次日”后刷新任务板。

#### 3.2 任务奖励

每个任务可以配置：

- 金币奖励。
- 固定材料。
- 概率掉落。
- 首次完成奖励。
- 事件链推进。
- 小镇状态变化。

LLM 可以提议任务主题和叙事关联，但不能直接决定金币、属性或掉率。

### 4. 道具品质与经济

统一使用五档品质颜色：

| 品质 | 颜色 | 用途 |
| --- | --- | --- |
| 普通 | 灰色 | 基础材料、普通食物和常见装备 |
| 优良 | 绿色 | 稳定的初级强化资源 |
| 稀有 | 蓝色 | 具有明显用途差异的装备或料理 |
| 史诗 | 紫色 | 特殊配方、角色偏好礼物或事件奖励 |
| 传说 | 金色 | 稀有事件、任务链终点或收藏内容 |

材料可以：

- 出售换取金币。
- 保留用于打造装备。
- 作为任务或事件条件。

这种选择应形成实际取舍：提前出售可以解决当前金币压力，但会推迟装备打造。

### 5. 装备打造

- 配方由材料和金币组成。
- 打造结果进入现有背包。
- 装备后直接影响战斗数值。
- 攻击属性增加角色伤害。
- 防御属性减少受到的伤害。
- 后续可以增加职业限制、套装或特殊效果，但不应在首个闭环中过度扩张。

### 6. 食物与补给

#### 6.1 远征行囊与携带限制

城镇背包用于长期持有材料、装备和礼物；进入副本时，玩家必须从城镇背包中编组一份独立的“远征行囊”。远征行囊有明确的格数或负重上限，限制的是本次远征可主动带入的补给，而不是永久限制玩家的仓库。

- 食物、绷带、镇定剂等消耗品占用行囊容量；
- 已装备在角色身上的装备不占用行囊；
- 材料、礼物和暂时无用途的道具默认不能带入副本；
- 任务可配置少量必带任务物品，并预留对应容量；
- 副本内获得的战利品先记录为本次远征收益，结算时统一进入城镇背包，不因行囊已满而丢失；
- 撤退、失败和通关都应清楚展示本次消耗与带回的收益。

该限制的目的在于制造出发前的取舍：带更多食物可以走得更远，带更多药品可以提高容错，但会挤占其他补给的位置。首版应使用固定格数和少量明确分类，暂不引入复杂重量单位或装备耐久系统。

食物和战斗消耗品必须分开：

- 食物：队伍行军与跨日消耗。
- 绷带、镇定剂等：战斗中主动使用。

基础规则：

- 每进入一个副本节点，全队消耗一份食物。
- 跨越新的一天时消耗城镇基础食物。
- 食物不足时仍允许继续前进，避免死档。
- 饥饿会造成生命、疲劳、攻击、防御或士气方面的惩罚。
- 玩家始终可以撤退。

料理可以提供短期效果：

- 普通干粮：只补充基础食物。
- 优良料理：少量恢复。
- 稀有料理：下一节点获得短期增益。
- 史诗或传说料理：用于特殊事件、节日或角色内容，不作为日常必需品。

### 7. 礼物、好感度与阶段化人设

金币的重要消耗出口之一是购买礼物。

礼物具有偏好标签，不同角色对同一礼物的反应不同。好感不能只靠无限赠礼提升：

- 每天或每次远征后限制有效赠礼次数。
- 普通阶段可以靠日常互动积累。
- 关键阶段必须完成个人事件才能突破。

建议的关系阶段：

| 阶段 | 人设表现 |
| --- | --- |
| 陌生 | 礼貌、克制、保持距离 |
| 熟悉 | 分享习惯、日常看法和轻量过去 |
| 信赖 | 谈论目标、恐惧、创伤和重要选择 |
| 羁绊 | 出现专属事件、更主动的关心与情感表达 |

关系阶段必须进入 LLM 提示上下文，改变称呼、语气、主动程度和允许透露的信息，而不只是替换固定台词。

### 8. LLM 的职责

#### 8.1 LLM 适合负责

- 角色自然对话。
- 根据好感阶段表现不同人设。
- 对礼物生成个性化反馈。
- 对任务结果生成评论、抱怨、庆祝或安慰。
- 形成短期和长期角色记忆。
- 生成每日新闻、小镇趣事、酒馆传闻。
- 在白名单模板中提议特殊任务。
- 把多个任务和事件线索串联成连续故事。

#### 8.2 LLM 不得直接负责

- 修改金币、经验、好感或属性。
- 创建任意装备数值。
- 决定未验证的奖励与掉率。
- 跳过未完成的前置条件。
- 生成不存在的地点、NPC、敌人或任务模板后直接执行。
- 直接写入游戏状态。

基本原则：

```text
游戏代码维护事实与规则。
LLM 负责表达、表演、联想和有限提议。
所有提议经过白名单校验后才能变成游戏行为。
```

### 9. 每日新闻与事件导演

每日生成器可以读取：

- 前一天完成、失败或撤退的任务。
- 当前游戏天数。
- 小镇资源和活跃事件链。
- 队伍等级与近期战利品。
- 角色关系阶段和关键记忆。
- 玩家近期关键选择。
- 天气、节日或剧情标记。

输出可以包括：

- 一条主新闻。
- 两到三条小镇趣事或传闻。
- NPC 对近期事件的看法。
- 一个经过验证后可加入任务板的特殊任务提议。
- 一个已存在事件链的后续节点。

生成结果必须保存到存档；同一天刷新页面不能重新随机生成完全不同的新闻和任务。

### 10. 结构化叙事协议

#### 10.1 XML 信封示例

```xml
<game_output version="1">
  <narrative>
    <news>
      <headline>北侧水渠再次传出怪声</headline>
      <body>两名磨坊工声称，昨夜看见蓝色微光顺流而下。</body>
    </news>
    <rumor speaker="innkeeper">
      最近采购药草的人突然多了起来。
    </rumor>
  </narrative>

  <actions>
    <action type="offer_quest" template="missing_person">
      <location>north_canal</location>
      <enemy_pool>slime,bandit_scout</enemy_pool>
      <followup>herbalist_rescue</followup>
      <reward_tier>2</reward_tier>
    </action>
  </actions>
</game_output>
```

#### 10.2 处理原则

游戏端不能直接信任 XML：

1. 定位 `<game_output>` 区间。
2. 清除 Markdown 代码围栏和标签外说明。
3. 尝试修正常见格式问题。
4. 解析 XML。
5. 校验版本、允许标签、属性、长度和枚举。
6. 验证任务模板、地点、敌人、NPC、奖励档位和事件状态。
7. 安全文本可以显示，非法动作必须丢弃。
8. 完全失败时使用本地模板。

即使模型原生支持结构化输出，也仍需进行语义校验。结构化能力只能保证形状，不能保证游戏逻辑正确。

### 11. 模型能力降级

不能假定用户模型支持原生结构化输出。

采用三级策略：

1. **原生结构化输出**：宿主和模型都支持时使用 Schema。
2. **普通文本＋XML**：不支持时通过提示词要求输出固定 XML。
3. **叙事降级**：XML 无法验证时，只保留新闻或对白；必要时使用本地模板。

Mobile-Tavern 后续可以提供能力查询：

```ts
interface LlmCapabilities {
  structuredOutput: boolean;
  streaming: boolean;
  maxContextTokens?: number;
}
```

格式修复优先使用本地确定性代码。只有内容完整但格式严重损坏时，才考虑再次请求模型整理。

### 12. 事件链状态

建议的通用事件链：

```text
未发现
→ 传闻出现
→ 前置任务开放
→ 前置任务完成
→ 后续事件开放
→ 分支任务或角色事件
→ 结局
→ 次日新闻与角色反馈
```

需要预留：

- 事件 ID 和版本。
- 当前节点。
- 前置条件。
- 是否看过。
- 是否失败或错过。
- 分支选择。
- 任务关联。
- 角色关联。
- 后续新闻标记。

具体事件内容可以逐步增加，但状态结构应尽早稳定。

### 13. 当前可玩性问题与优化方向

> 状态：已落地（§13.2 战斗深度、§13.3 成长反馈、§13.4 UI 信息层级均已实现）
> 背景：核心系统已闭环，但实际体验后判定当前可玩性不足，需优先打磨现有玩法深度，而非继续扩张新系统。

#### 13.1 问题清单

| 问题 | 表现 | 影响 |
| --- | --- | --- |
| 成长反馈弱 | 升级与装备带来的数值差距小，玩家感受不到变强 | 缺乏长期养成动力 |
| 战斗没深度 | 仅靠攻击距离与站位，缺少职业差异化和决策点 | 远征过程单调 |
| UI 不够好 | 管理页、战斗页视觉与交互信息层级不清晰 | 沉浸感与操作效率打折 |

#### 13.2 战斗深度优化

为三个职业增加被动技能，使站位与职业组合产生实际差异：

| 职业 | 被动技能 | 效果 |
| --- | --- | --- |
| 先锋 | 坚守 | 前排时受到伤害降低，并对贴身敌人有反制 |
| 斥候 | 锐眼 | 后排时提升命中率与暴击，可优先攻击远程敌人 |
| 术士 | 共鸣 | 同排有队友时强化法术伤害，单独站位时减弱 |

实现要点：

### 14. 近期方向调整：自由叙事优先于传统主线

> 状态：已确认。用于约束后续内容设计和排期。

#### 14.1 不采用线性强制主线

游戏不应要求玩家按固定章节、固定日期或唯一任务顺序推进。这样会让 {{user}} 作为队长的自主决定变成表面选择，也会把 LLM 的自由交流限制成只能复述既定剧本。

后续采用“目标框架 + 可变路径”的结构：

- 代码维护可验证的世界状态、区域威胁、任务前置和结局条件；
- 玩家可通过远征、宿舍交流、镇内行为或暂时搁置目标，决定处理问题的顺序与态度；
- LLM 可以根据已发生的事情解释人物动机、生成反馈、提出符合白名单的线索或建议；
- LLM 不能凭空确认剧情事实、直接完成目标，或改写奖励和状态；
- 关键结果由明确的状态条件触发，而非由模型判定。

因此，“主线”在游戏内应更像持续出现的远征目标、传闻和人物牵挂，而不是压在玩家头上的任务清单。第一阶段只需建立少量可反复回应玩家选择的事件钩子，不急于制作完整章节脚本。

#### 14.2 招募改为后期内容

当前优先保证初始三名队员在战斗、宿舍和对话中的完整体验。新增可招募角色会同时要求立绘、宿舍姿态、战斗立绘/动作、语音或文本人格、装备适配、关系事件及测试，制作成本很高；在基础美术与战斗表现尚未统一时，不应以“角色数量”换取表面的内容量。

近期约束：

- 不新增招募入口、招募货币或新的可玩角色；
- 已存在但尚未完整制作的角色不作为近期玩法承诺；
- 先完成三名初始成员的职业技能、战斗反馈、日常互动和状态触发的 LLM 场景；
- 待美术生产流程稳定、角色表现模板成熟后，再以一个角色为单位制作完整招募内容。

#### 14.3 更新后的优先级

1. 初始三人职业技能、敌人机制与远征结算，形成可靠的战斗体验；
2. 用“传闻 / 事件钩子 / 可变任务后果”建立轻量目标框架，不做强制线性主线；
3. 完善三人的宿舍互动、状态触发的 LLM 场景与 LLM 上下文；
4. 统一现有页面和战斗资产的视觉表现、可读性与音效；
5. 在上述模板验证完成后，才开始制作新的招募角色与对应美术资源。

### 15. 初始三人：人物设定草案

> 状态：第一版。用于宿舍自由对话、远征事件反应与后续关系事件；不作为强制主线。

#### 岚 · 先锋

岚曾在边境前哨担任守卫。一次护送任务因遗迹异动失控，他是最后带着幸存者回到城里的人；从那以后，他不轻易承诺，也不喜欢把队友当作可以交换的筹码。

- 外在：寡言、做事有次序、先检查门窗和补给再谈别的；
- 内在：对“没能带所有人回来”仍有愧疚，因此会过度承担风险；
- 对队长：起初把 {{user}} 当作需要评估的指挥者，信赖后会主动讨论最坏情况；
- 关键词：守夜、责任、旧军章、热茶、不要逞强。

#### 雾 · 游侠

雾在商路与山林之间长大，靠替人带路、找遗失货物和躲开麻烦谋生。他很会让场面轻松，也很会记住每一条撤退路线；笑得最自然的时候，往往正是他最紧张的时候。

- 外在：健谈、机灵、喜欢调侃气氛过于严肃的人；
- 内在：害怕被困住或被留下，不愿直接谈及过去的搭档；
- 对队长：喜欢试探队长的反应，认可后会把真正观察到的危险先告诉 {{user}}；
- 关键词：地图、风向、小赌、山果、逃跑不是失败。

#### 星罗 · 术士

星罗原本在星辉塔学习星术，却因为总想亲自验证书上没有写完的部分而离开。遗迹的回声、封印和失落的法阵对她有近乎危险的吸引力；她不是不害怕，而是认为害怕也值得被弄明白。

- 外在：好奇、直率、容易为一个发现忘记时间；
- 内在：担心自己只会制造麻烦，因而很在意队友是否愿意听她解释；
- 对队长：会主动分享推测和发现，但必须学会接受 {{user}} 的“先撤退”；
- 关键词：星图、笔记、封印、甜食、再看一眼。

#### 三人的初始关系

- 岚会压住雾过度冒险的提议，却也承认雾的直觉常常救人；
- 雾喜欢逗星罗，但会在她陷入研究时替她观察周围；
- 星罗尊敬岚的稳定，也会温和地指出他把责任背得太多；
- {{user}} 不是参战单位，而是三人共同承认的队长。人物冲突可以向队长倾诉、讨论或保留，不应自动替玩家做决定。

### 16. 压力系统当前状态

当前代码中的 `morale` 实际承担的是“压力”数值：受击和冒险事件会提高它，镇定剂与休整会降低它；达到阈值后会降低攻击力。它已经能支持远征中的风险选择，但名称、UI 和后果尚未完全统一。

近期暂定规则：

- 0 表示平静，数值越高表示压力越大；
- 事件探查、受击会增加压力，安全休整和镇定剂会降低压力；
- 暂不加入恐慌、离队或永久惩罚，避免首版把失败感放大；
- 后续将把界面中的“士气”统一改名为“压力”，并为不同角色加入不同的压力反应文本。
